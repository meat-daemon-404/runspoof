# 03 · 判定规则怎么摸清

> ⚠️ **这一篇不列具体数值。**
>
> 每所学校在同一个 App 里配置的考核标准都不一样——时间窗、配速区间、步频区间、里程上下限、打卡点数量与位置，全都是学校自己在后台设的。把某一所学校的数字写进文档，对别人就是错的，对自己也会随学期变化而失效。
>
> 所以这一篇只讲**怎么把你这所学校的规则摸出来**，以及摸出来之后怎么映射成模块参数。

---

## 1. 为什么要自己摸

这类 App 的判定是**三层叠加**的：

| 层 | 判什么 | 在哪能看到 |
|---|---|---|
| 客户端 | 位置、配速、步频、打卡 | 跑步界面的实时数字与红字提示 |
| 服务端 | 速度序列自洽性、点位合法性 | 结果页的「未达标原因」 |
| 风控 | 模拟定位痕迹、设备指纹、身份 | 一般看不到，直接判无效 |

只看模块日志是不够的——模块能让数据「看起来对」，但**规则是学校定的，只有 App 界面和结果页会告诉你**。

---

## 2. 摸规则的固定动作

### 2.1 先看「跑区」页

打开 App 的跑步页，不点开始，先看地图：

- **绿色的框** = 学校下发的有效区域。这是整件事里唯一无法通用化的参数，必须照它画。
- **带编号的图标** = 打卡点。记下有几个、大致在框里的什么位置。
- 界面上的红字（如「不在有效区域内」「当前跑区不在有效时间内」）= 当前的卡点，逐条消掉。

### 2.2 再看规则说明页

学校通常会在 App 里放一页「跑步规则 / 成绩说明」，写明：

- 有效时间段（例如只允许早上某两小时）
- 有效配速区间与步频区间
- 单次最低里程、每日上限
- 必修次数 / 学期总里程

**把这些数字抄下来**，它们直接决定模块的速度与步频参数怎么填。

### 2.3 最后用一次真实跑步验证

规则页写的和实际判的经常不一致（尤其是时间窗）。最省事的验证方式：

1. 按规则页的数字设好模块参数，跑一次
2. 看结果页的「未达标原因」——它会明确告诉你卡在哪一条
3. 改一条，再跑一次

结果页的文案是这个 App 最诚实的部分，比任何文档都准。

---

## 3. 数值怎么映射成模块参数

摸到规则之后，换算关系只有三条：

### 3.1 配速 ↔ 速度

```
配速(分/公里) = 1000 ÷ 速度(m/s) ÷ 60
速度(m/s)     = 1000 ÷ (配速 × 60)
```

模块界面直接显示换算后的配速，不用手算。

**取值策略**：不要贴着区间上下限。上下限附近任何一次位置抖动或瞬时速度波动都可能被判越界，往里收一点更稳。

### 3.2 步频与速度要自洽

步频不能随便填一个落在区间里的数——**步频 × 步幅 = 速度**，三者必须自洽，否则风控会判「机械摇手机」。

常见的人类步态参考：

| 状态 | 步幅 | 步频 |
|---|---|---|
| 快走 | 1.0 ~ 1.2 m | 100 ~ 120 SPM |
| 慢跑 | 0.8 ~ 1.0 m | 160 ~ 180 SPM |
| 中速跑 | 1.0 ~ 1.3 m | 175 ~ 190 SPM |

模块的默认组合落在「慢跑」这一档，是最不容易被挑刺的姿态。

### 3.3 路线形状

**默认必须是闭合环**，不能是直线：

- 直线跑一次就出界，后面全程判「不在有效区域内」
- 闭合环才能持续满足「在区域内」，并且反复经过打卡点

环的周长决定单圈耗时。如果学校有「单次最低里程」，用 `目标里程 ÷ 周长` 估算要跑几圈，确认能在有效时间窗内跑完。

**还有一条比形状更隐蔽的：坐标系。** 你在编辑器里看到的底图是高德瓦片，那是 GCJ-02；App 判区用的是 WGS-84，两者在国内差 300~500 米。如果路线画得「形状完全对、位置整体偏移」，先怀疑这个，不要怀疑自己点错了。本模块的 `Geo` 类会自动转换；如果你自己改代码或换工具，这一步漏了就会一直是「形状对但位置错」。详见 [00-踩坑总览](00-踩坑总览.md) 的 B0 节。

---

## 4. 打卡点：距离判定就够了，但时间必须先对

打卡点在地图上是编号图标，轨迹经过某点 N 米内就记为「碰到」，进度条跟着走 `1/5 → 2/5 → … → 5/5`。**闭合环路线能正常把 5 个点全部打卡**，不需要按编号重排路径。

真正会把成绩作废的不是点位顺序，是**设备时间**：

```
为了您跑步记录的有效性，请修改为准确的北京时间后再上传记录
```

App 拿设备时间去跟服务端下发的跑区时间段比对，差几个小时就拒绝上传。这时你已经跑完、5/5 全打卡、里程配速步频全部正常，成绩照样传不上去。跑之前先校准设备时间（见 [06-完整使用教程](06-完整使用教程.md) 的「必须校准设备时间」一节）。

> **一条被推翻的旧结论**：本节早期写过「打卡要求按 1→2→3→4→5 顺序依次通过，闭环做不到」。那是把 2026-10-18 一次 0.00 公里旧记录的结果页当成了后来 5/5 那场的结论——两场不同，前者配置根本没打通。闭合环实际打卡正常。详见 [00-踩坑总览](00-踩坑总览.md) 的 G3 节。

判断「结果页这条原因是不是你这场的」的方法：结果页顶部有时间段（形如 `2026/10/18 21:09-21:39`），先核对它跟你的跑动时间对不对得上。

## 5. 服务端还会看什么

即使客户端全绿，服务端仍会独立校验。静态分析这类 App 的 so 库和 dex，能看到大致三类：

### 5.1 速度序列重算

App 上报的往往不是「一个平均配速」，而是**分段的瞬时速度序列**。服务端会：

- 对序列积分重算总距离
- 检查相邻区间的速度跳变（人类跑步的速度变化是连续的，突变即异常）
- 检查速度与位置点是否自洽

**这就是为什么只改坐标一定失败**——坐标改了但速度序列没跟上，两者对不上。

模块的做法是让位置、速度、朝向**由同一个时间函数派生**，天然自洽。

### 5.2 点位合法性打分

对每个上报点，按维度打分：时间戳是否连续递增、相邻点距离/时间差是否在人类范围、精度值是否合理、卫星数是否 > 0。

模块逐项对应：精度给一个合理固定值、卫星状态合成正常数量的星、时间戳按系统时钟递推。

### 5.3 风控维度

- 系统里的「模拟位置」开关状态
- `Location.isFromMockProvider()`
- `Location.getExtras()` 里有没有模拟定位标记
- root / Xposed 痕迹
- AppOps 里相关操作的状态

模块把这些逐个清掉（`hookAntiCheat`），但这只是**输入侧自洽**。

> **必须说清楚**：真实业务系统通常还叠加了设备指纹、极验/易盾类风控、人脸核身、姿态识别等。本模块一个都没处理。**它能骗过数据校验，骗不过身份校验。**

## 6. 参数速查

```java
// RouteEngine.java —— 这些是示例值，按你摸到的规则改
CENTER_LAT   = 0.0;         // 0,0 = 用户还没设过路线
CENTER_LNG   = 0.0;
RADIUS_DEG   = 0.00035;     // ≈ 39 m
SPEED_MPS    = 2.4;         // 换算成配速由 ConfigStore.paceText() 显示
BASE_CADENCE = 172.0;       // SPM
```

验证方法：构建、装模块、开跑，然后看

```bash
adb logcat -s RunSpoof:V
# system hooks installed, route=398m, center=<你在编辑器里保存的中心点>
```

`route=` 后面是**实际路径的周长**，不是半径换算出来的值：

- 用「跑道圈」按钮生成的 24 点椭圆，半径 39 m → 约 **398 m**（两直道 `4r` + 两半圆 `2πr`）
- 手画的多边形 → 按每段实算累加，点越多越接近真实跑道周长

**关键看 `center=`**：必须等于你在编辑器里保存的中心点。如果还是 `0.0,0.0`，说明配置没读到，去查 [00-踩坑总览 D1](00-踩坑总览.md)。
