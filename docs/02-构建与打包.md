# 02 · 构建与打包

本仓库**不含 Gradle**。原因很实际：这东西是在一台没有 Android Studio、没有完整 SDK、只有 `build-tools/34.0.0` 和 `platforms/android-34` 的机器上手搓出来的。后来发现无 Gradle 反而更好——整条链就六个步骤，每一步失败原因都看得见。

`build.ps1` 就是这条链的固化版本。

---

## 快速跑

```powershell
.\build.ps1 `
    -Sdk 'D:\Project\toolchain\android-sdk' `
    -Jdk 'D:\Project\toolchain\jdk17' `
    -ApiJar 'D:\_tools\lsposed-dl\api102\classes.jar'
```

产出 `dist\RunSpoof-v41.apk`。

| 参数 | 作用 |
|---|---|
| `-Sdk` / `-Jdk` / `-ApiJar` | 三个必需依赖的路径，不传则用脚本里写死的默认值 |
| `-OutDir` | 产物目录，默认 `dist\` |
| `-VersionCode` / `-VersionName` | 默认 `41` / `3.3`（与当前 Release 对齐） |
| `-NoSign` | 只出未签名对齐包 |
| `-Keystore` / `-KsAlias` / `-KsPass` | 指定自己的 keystore；不传则生成临时调试库 |

## 六个步骤，以及每一步为什么必须这样写

### 1. javac

```powershell
& $Javac --release 11 -encoding UTF-8 -nowarn `
    -cp "$AJ;$ApiJar" -d $Cls $Sources
```

- `--release 11`：`d8 --min-api 26` 配 Java 11 字节码最稳。用 17 的默认 target 也能过，但 `d8` 偶尔会在 `invokedynamic` 上多绕一圈。
- `-encoding UTF-8`：源码里有中文注释。**不加这个，中文 Windows 上 javac 按 GBK 读，直接编译错。**
- `-cp` 用**分号**分隔（Windows）。`api102/classes.jar` 提供 `io.github.libxposed.api.*`。

产物 `build\classes\` 下应有 **17 个 `.class`**（6 个源文件 + 匿名内部类）。少于这个数说明有文件没编进去。

---

### 2. d8

```powershell
& $D8 --min-api 26 --release --lib $AJ --lib $ApiJar --output $Dex @ClassFiles
```

- `--min-api 26`：模块 manifest 里 `minSdkVersion` 也是 26，保持一致。
- `--lib` 传两次：`android.jar` 和 `api102/classes.jar` 都是**只在编译期需要、运行时由框架提供**的库。不传 `--lib` 的话 d8 会尝试把它们打进 dex，或者报一堆 missing class。
- 产物 `build\dex\classes.dex`，约 **64 KB**。

> 实测 `--release` 和 `--debug` 出来的 dex 大小差不多，直接用 `--release`。

---

### 3. aapt2 link

```powershell
& $Aapt2 link -o $BaseApk -I $AJ `
    --manifest AndroidManifest.xml `
    --min-sdk-version 26 --target-sdk-version 34 `
    --version-code $VersionCode --version-name $VersionName
```

这一步只处理 `AndroidManifest.xml`。**没有 `-A assets`**，这是刻意的——见下一步。

---

### 4. 打包 dex + `META-INF/xposed/`（本流程最关键的一步）

```powershell
Push-Location $Stage      # $Stage 里放 classes.dex 和 META-INF/xposed/* 
& $Jar uf $BaseApk classes.dex
& $Jar uf $BaseApk 'META-INF\xposed\module.prop' `
                   'META-INF\xposed\scope.list' `
                   'META-INF\xposed\java_init.list'
Pop-Location
```

**为什么不用 `aapt2 -A assets`**：

| 做法 | APK 里的条目 | LSPosed 识别 |
|---|---|---|
| `aapt2 -A assets`（`assets/META-INF/xposed/`） | `assets/META-INF/xposed/module.prop` | ❌ 在 assets 下，只查根目录 |
| `aapt2 -A assets`（`META-INF/xposed/`） | `META-INF\xposed\module.prop` | ❌ 反斜杠，ZIP 规范要求 `/` |
| **`jar uf`（本脚本）** | `META-INF/xposed/module.prop` | ✅ |

两种失败方式**都不报任何错**。APK 装得上，LSPosed 列表里也看得到模块，就是永远不加载。这个坑踩了两次才定位到。

`jar.exe` 是 JDK 自带的，写进去的条目名就是标准正斜杠。

---

### 5. zipalign

```powershell
& $Zipalign -f -p 4 $BaseApk $Aligned
```

- `-p` 让 `.so` 按页对齐。本模块没有 `.so`，但带着没坏处。
- `-f` 覆盖已有文件。
- **必须在签名之前做**。签名后再 align 会把签名破坏掉。

---

### 6. apksigner

```powershell
& $Apksigner sign `
    --ks $Keystore --ks-type PKCS12 --ks-key-alias $KsAlias `
    --ks-pass "pass:$KsPass" --key-pass "pass:$KsPass" `
    --min-sdk-version 26 `
    --out $Final $Aligned
```

- `--ks-type PKCS12` 显式指定。JDK 17 的 `keytool` 默认产出仍可能被识别成 JKS，不指定时偶发读不出 alias。
- 生成密钥库时也要显式 `-storetype PKCS12`：

```powershell
& $Keytool -genkeypair -v `
    -keystore build\debug-keystore.p12 -storetype PKCS12 `
    -alias runspoof -keyalg RSA -keysize 2048 -validity 10000 `
    -storepass runspoof -keypass runspoof `
    -dname "CN=RunSpoof Debug, OU=Dev, O=Local, L=Local, S=Local, C=CN"
```

> **签名密钥不要入库**。`.gitignore` 里已经排除了 `*.jks` / `*.keystore` / `*.p12` / `*.pfx`。
> 不传 `-Keystore` 时脚本会在 `build\` 下生成临时调试库，`build/` 整个被忽略，所以默认路径下不会泄露。

## 自校验：为什么脚本最后要解压 APK 看条目

```powershell
$zip = [System.IO.Compression.ZipFile]::OpenRead($Final)
$names = $zip.Entries | ForEach-Object { $_.FullName }
$zip.Dispose()

$required = @('META-INF/xposed/module.prop', 'META-INF/xposed/scope.list',
              'META-INF/xposed/java_init.list', 'classes.dex', 'AndroidManifest.xml')
$missing = $required | Where-Object { $names -notcontains $_ }
if ($missing) { ... exit 1 }
```

这段**不要删**。

它的存在理由是前面那个坑：错误形态不报错。人眼很难发现 `META-INF\xposed\module.prop` 和 `META-INF/xposed/module.prop` 的区别——终端里看着几乎一样。所以让脚本自己解压、逐条比对字符串。

期望输出：

```
==> APK 条目：
      AndroidManifest.xml
      classes.dex
      META-INF/
      META-INF/xposed/
      META-INF/xposed/module.prop
      META-INF/xposed/scope.list
      META-INF/xposed/java_init.list
      ...
==> 校验通过：META-INF/xposed 在 APK 根目录，正斜杠命名。
```

## PowerShell 的两个陷阱

### 陷阱一：`build.ps1` 必须存成 UTF-8 **with BOM**

Windows PowerShell 5.1 对**无 BOM** 的文件按系统 ANSI 代码页解码。中文环境下是 936/GBK，中文注释的字节被误解码后可能产生引号、花括号之类的字符，直接把脚本语法搞坏，报一堆莫名其妙的 `Unexpected token`。

修：

```powershell
$p = '.\build.ps1'
$txt = [System.IO.File]::ReadAllText($p, (New-Object System.Text.UTF8Encoding($false)))
[System.IO.File]::WriteAllText($p, $txt, (New-Object System.Text.UTF8Encoding($true)))
```

（PowerShell 7 默认按 UTF-8 读，没这个问题。脚本里仍然保留注释说明，因为很多人机器上还是 5.1。）

### 陷阱二：`$ErrorActionPreference` 必须是 `Continue`，不能是 `Stop`

`javac`、`keytool`、`apksigner` 都会往 **stderr** 写正常信息：

```
注意: 某些输入文件使用或覆盖了已过时的 API。
正在为以下对象生成 2048 位 RSA 密钥对...
```

`Stop` 模式下 PowerShell 把原生程序的 stderr 当成 `ErrorRecord`，直接终止脚本。于是构建「莫名其妙地成功了一半然后退出」。

正确写法：

```powershell
$ErrorActionPreference = 'Continue'
# ...
& $Javac ...
if ($LASTEXITCODE -ne 0) { Fail "javac 失败（rc=$LASTEXITCODE）" }
```

用 `$LASTEXITCODE` 判断，不用 `$?`，也不靠异常。

## 手工复现（不用脚本）

万一脚本跑不起来，按顺序手敲这六条也能出包：

```powershell
$Jdk = 'D:\Project\toolchain\jdk17'
$Bt  = 'D:\Project\toolchain\android-sdk\build-tools\34.0.0'
$AJ  = 'D:\Project\toolchain\android-sdk\platforms\android-34\android.jar'
$API = 'D:\_tools\lsposed-dl\api102\classes.jar'
$env:JAVA_HOME = $Jdk
$env:PATH = "$Jdk\bin;$env:PATH"

# 1
& "$Jdk\bin\javac.exe" --release 11 -encoding UTF-8 -nowarn -cp "$AJ;$API" -d build\classes src\com\qf\runspoof\*.java

# 2
& "$Bt\d8.bat" --min-api 26 --release --lib $AJ --lib $API --output build\dex build\classes\com\qf\runspoof\*.class

# 3
& "$Bt\aapt2.exe" link -o build\out\base.apk -I $AJ --manifest AndroidManifest.xml --min-sdk-version 26 --target-sdk-version 34 --version-code 10 --version-name 1.7

# 4
Copy-Item build\dex\classes.dex build\stage\classes.dex -Force
New-Item -ItemType Directory -Force build\stage\META-INF\xposed | Out-Null
Copy-Item assets\META-INF\xposed\* build\stage\META-INF\xposed\ -Force
Push-Location build\stage
& "$Jdk\bin\jar.exe" uf ..\out\base.apk classes.dex
& "$Jdk\bin\jar.exe" uf ..\out\base.apk 'META-INF\xposed\module.prop' 'META-INF\xposed\scope.list' 'META-INF\xposed\java_init.list'
Pop-Location

# 5
& "$Bt\zipalign.exe" -f -p 4 build\out\base.apk build\out\aligned.apk

# 6
& "$Bt\apksigner.bat" sign --ks build\debug-keystore.p12 --ks-type PKCS12 --ks-key-alias runspoof --ks-pass pass:runspoof --key-pass pass:runspoof --min-sdk-version 26 --out build\out\RunSpoof-v41.apk build\out\aligned.apk
```

## 构建产物参考值

以下是 v3.3（versionCode 41）实际构建出来的大小，可用来对照自己的构建结果是否正常：

| 产物 | 大小 | 说明 |
|---|---|---|
| `build\classes\` 17 个 `.class` | 100,669 B | `RunSpoofModule.class` 单独 27,377 B |
| `build\dex\classes.dex` | 80,628 B | d8 输出 |
| `build\out\base.apk`（aapt2 link 刚出来时） | ~1.3 KB | 只有 manifest 和 resources.arsc |
| `build\out\base.apk`（`jar uf` 塞完 dex 和 META-INF 后） | 39,771 B | 下一步 zipalign 的输入 |
| `build\out\aligned.apk` | 39,772 B | zipalign 对齐后，只多 1 字节 |
| **`dist\RunSpoof-v41.apk`** | **49,783 B** | 签名后的最终包（签名块约 10 KB） |

APK 小于 30 KB 或大于 60 KB 都值得怀疑——前者可能 dex 没塞进去，后者可能混进了 assets。

## 同样的代码，两次构建出来的 APK 哈希为什么不同

这是唯一一个看起来像 bug、其实不是的现象。第一次遇到会怀疑构建链有问题，实测两次构建后做个对比就能看清：

```
AndroidManifest.xml            same
classes.dex                    same
resources.arsc                 same
META-INF/MANIFEST.MF           same
META-INF/RUNSPOOF.RSA          same
META-INF/RUNSPOOF.SF           same
META-INF/xposed/java_init.list same
META-INF/xposed/module.prop    same
META-INF/xposed/scope.list     same
```

九个条目**内容逐字节相同**，但整包 SHA-256 不同。差别在 zip 条目头里那两个时间字段：

```
classes.dex              old=20486/23891   new=20579/23891
META-INF/MANIFEST.MF     old=20486/23891   new=20579/23891
META-INF/RUNSPOOF.RSA    old=20486/23891   new=20579/23891
META-INF/RUNSPOOF.SF     old=20486/23891   new=20579/23891
```

`20486` 是 MS-DOS 格式的时间字（秒数除以 2 后左移，再或上时和分）。两次构建间隔几秒，这里就跟着变。前面几个条目（manifest、resources.arsc、META-INF/xposed/*）是 `jar uf` 从磁盘上的固定文件带进去的，或由 aapt2 写成常量，时间戳稳定；`classes.dex` 和三个签名文件是本次构建现生成的，时间戳就是构建时刻。

**所以验证一个 APK 是不是"同一个东西"，要比对解包后的条目哈希，不能比整包哈希。** 整包哈希只能证明"这个文件没被人改过"，不能证明"这是同一份代码构建的"。

反过来也成立：如果你改了代码，`classes.dex` 的条目哈希会变；如果只是重新跑了一次构建，它不会变。
