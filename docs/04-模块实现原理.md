# 04 · 模块实现原理

按「目标 App 的判定维度」逐层拆。每一节回答同一个问题：**这一层挂在哪、为什么必须挂在这**。

整体结构：

```
RunSpoofModule extends XposedModule
  ├─ onModuleLoaded()      → 只打日志
  └─ onPackageLoaded()     → 只对 TARGET_PKG 生效
       ConfigStore.attach(this)   ★ 第一件事
       RouteEngine.ensureInit()
       hookAMap()            ← 高德 SDK（App 真正的定位来源）
       hookLocationManager() ← 系统定位（兜底 + listener 捕获）
       hookGnss()            ← 卫星状态
       hookSensors()         ← 加速度计/计步器拦截
       hookWifi()            ← WiFi 扫描结果
       hookTelephony()       ← 基站信息
       hookAntiCheat()       ← mock 标记 + 坐标 getter 覆盖
       startDispatchers()    ← 三个定时派发
```

## 1. 定位：为什么必须 hook 高德

目标 App 的定位走**高德定位 SDK**，而 SDK 的类在**App 自己的 classes.dex** 里（不是独立的 so/ jar）。这意味着：

- `AMapLocation` **继承** `android.location.Location`，但内部有自己的 `mLatitude`/`mLongitude` 字段
- SDK 拿数据不走 `LocationManager.getLastKnownLocation()`，所以 hook 系统层**完全无效**
- `AMapLocation.getLatitude()` 读的是自己字段，不是 `Location.getLatitude()`

### 1.1 hook 了哪些

`hookAMap()`：

| 方法 | 返回 |
|---|---|
| `getLatitude` / `getLongitude` | `RouteEngine.positionAt(now)` |
| `getAltitude` | `100.0`（任意海拔） |
| `getSpeed` | `RouteEngine.currentSpeed(now)` |
| `getBearing` | `RouteEngine.bearingAt(now)` |
| `getAccuracy` | `4.0f` |
| `getSatellites` | `20` |
| `getLocationType` / `getGpsAccuracyStatus` | `1`（GPS 定位） |
| `getErrorCode` | `0` |
| `isSuccess` | `true` |

还有两个**构造函数**（`()` 和 `(String)`）：构造完立刻 `fillAmapLocation()` 填字段。这是为了防止 SDK 刚 new 出来、还没被 getter 覆盖的瞬间泄露 `(0,0)`——那种点位会被 App 的 `isValidPoint` 一击判死。

### 1.2 为什么 getter 和字段都要写

- App 若调 `getLatitude()` → 命中 hook
- App 若直接读字段（高德 SDK 内部有这种路径，尤其在 `doLocationChanged` 里做距离计算时） → 命中 `fillAmapLocation` 写进去的值

两处都给同一时刻的值，才不会自相矛盾。

### 1.3 `hookOne` 为什么要沿继承链查找

```java
private void hookOne(Class<?> clazz, String methodName, Class<?>[] paramTypes,
                     XposedInterface.Hooker hooker) {
    Class<?> cur = clazz;
    while (cur != null) {
        try {
            Method m = cur.getDeclaredMethod(methodName, paramTypes);
            m.setAccessible(true);
            hook(m).intercept(hooker);
            return;
        } catch (NoSuchMethodException ignored) {
            cur = cur.getSuperclass();
        }
    }
}
```

旧版只用 `clazz.getDeclaredMethod(...)`。如果方法其实声明在父类，就 `NoSuchMethodException` 然后被 catch 忽略掉——**日志上看是「hook 成功」，实际一个都没挂上**。这种静默失败排查起来极其费时，所以现在沿继承链逐级找。

## 2. 系统定位层（兜底）

`hookLocationManager()`：

| 目标 | 处理 |
|---|---|
| `getLastKnownLocation(String)` | 直接返回 `Factory.buildLocation(provider)` |
| `getCurrentLocation(...)` | 同上 |
| `isProviderEnabled` / `isLocationEnabled` | 恒 `true` |
| `getProviders` / `getAllProviders` | 返回 `[gps, network, passive, fused]` |
| `requestLocationUpdates(...)` | **捕获 listener，然后 `chain.proceed()`** |

### ★ 这一层最大的坑：`requestLocationUpdates` 不能吞掉注册

早期实现：

```java
// 错误写法
hook(m).intercept(chain -> {
    registerLocationListener(chain.getArg(idx));
    return null;   // ← 想「吞掉」注册，改由模块主动推
});
```

结果 App **一次定位回调都收不到**。原因：系统层面从未建立位置请求，`dumpsys location` 里 listeners 为空。模块后来主动调用的 `onLocationChanged` 也**没有接收方**——因为注册根本没发生。

正确写法：

```java
hook(m).intercept(chain -> {
    registerLocationListener(chain.getArg(idx));   // 记下来，备用
    return chain.proceed();                        // ★ 必须放行
});
```

系统正常注册，App 正常进回调；模块只是**额外**推一份伪造数据（每秒一次，`startDispatchers` 里）。

### 2.1 `Location` getter 覆盖，按时间戳算坐标

```java
hookOne(Location.class, "getLatitude", new Class<?>[]{}, chain -> {
    double[] p = positionOf(chain.getThisObject());
    return p[0];
});
```

```java
private static long timeOf(Object loc) {
    // ★ 读 elapsedRealtime，不读 getTime()。
    // getTime() 会被模拟器的假 GPS 污染，用它反查坐标会让位置瞬移，
    // 分段算出 60km/h 的鬼魂速度。见 docs/00 B6。
    Location l = (Location) loc;
    long clean;
    try {
        long rtNs = l.getElapsedRealtimeNanos();
        clean = rtNs > 0L ? Clock.wallMsForRt(rtNs / 1_000_000L) : Clock.nowMs();
    } catch (Throwable ignored) {
        clean = Clock.nowMs();
    }
    watchTimelineDrift(clean);
    return clean;
}

private static double[] positionOf(Object loc) {
    return RouteEngine.positionAt(timeOf(loc));
}
```

### ★ 为什么必须用「对象自己的时间戳」而不是「当前时间」

旧版全部用 `System.currentTimeMillis()`。后果：

`Location.distanceTo(other)` 内部读**两个对象各自的**经纬度。两个对象调 `getLatitude()` 时都拿到**当前时刻**的坐标 → 两点重合 → **距离恒为 0**。

App 用 `distanceTo` 逐点累加里程，于是**里程永远 0 米**。

改成按每个对象自己的时间之后，不同时刻创建的 Location 自然映射到轨迹上不同位置，`distanceTo` 恢复正确。

> ⚠️ 但**取这个时间的来源必须是 `elapsedRealtimeNanos`，不是 `getTime()`**。
> 早期版本这里写的是 `location.getTime()`，方向对、来源错，导致成绩被判
> 「分段不达标」。完整推导和证据见 [00-踩坑总览 B6](00-踩坑总览.md)。
>
> 同时 `getTime()` 本身也要接管（App 的分段边界就是拿它算的），
> 接管后它与坐标共用同一条由 `Clock` 提供的时间轴。
> 注意 `timeOf()` 内部**不能再调 `getTime()`**——那会无限递归。

> 这条和 C1 的「步频恒为 0」是本项目两个最典型的「看起来生效了但数据是错的」类 bug。

### 2.2 为什么删掉了 setter 接管

旧版还 hook 了 `setLatitude` / `setLongitude` / `setSpeed` / `setBearing` 并 `return null`，本意是「防止别处写值导致 getter 不一致」。

但 getter 已经按时间戳算了，**根本不读字段**。而 `Location.distanceTo()` / `distanceBetween()` 走的是 **native 代码直接读 `mLatitude`/`mLongitude` 字段**。setter 被吞掉 → 字段永远是 0 → 距离恒 0。

现在：**不拦 setter**。`Factory.buildLocation()` 额外用反射把字段也写成一致的值，让 getter 和 native 读取两条路径都对得上。源码里在对应位置留了注释，不要「优化」回去。

## 3. GNSS：卫星状态用新对象重放

```java
hookSingleGnssCallback(cb, cl);   // hook 每个 callback 的 onSatelliteStatusChanged
```

```java
hook(m).intercept(chain -> {
    Object spoofed = Factory.buildGnssStatus(cl, 18);
    if (spoofed != null) {
        return chain.proceed(new Object[]{spoofed});   // ★ 用新参数重放
    }
    return chain.proceed();
});
```

### ★ 为什么不能改 `chain.args[0]`

Android 15 上 `GnssStatusTransport.onSvStatusChanged` 的参数是 `ImmutableList`。`chain.args[0] = spoofedStatus` 抛：

```
java.lang.UnsupportedOperationException: null
  at java.util.Collections$UnmodifiableList.set(...)
```

异常发生在 `proceed()` **之前**，于是**真实回调也被吞掉了**。App 侧表现是「GPS 信号弱」——它一次卫星状态都没收到。

正确做法：`GnssStatus.Builder` 造新对象，`chain.proceed(new Object[]{newStatus, ...})` 单独传参，不碰 `args`。

> `Factory.buildGnssStatus` 用 `AppOpsManager`/`GnssStatus.Builder` 反射构造：先 `Builder()`，`addSatellite(...)` 18 次，再 `build()`。同时必须保留原参数里其余位置的值（有的重载有多个参数），所以实现了 `proceed(Object[])` 的完整替换版本。

## 4. 传感器：拦截注册 + 高频派发

### 4.1 注册/注销拦截

候选类：`android.hardware.SystemSensorManager` 和 `android.hardware.SensorManager` 都试（不同 Android 版本注册方法在哪个类上不一样）。

匹配规则：方法名 `startsWith("registerListener")` / `startsWith("unregisterListener")`，且参数里有 `SensorEventListener`，再找参数里的 `android.hardware.Sensor`。

### ★ 4.2 key 必须用 (listener, sensor) 组合

```java
private static String key(Object listener, Object sensor) {
    return System.identityHashCode(listener) + "#" + System.identityHashCode(sensor);
}
```

旧版用 listener 做 key。同一个 listener 注册**加速度计 + 陀螺仪**时，第二次 `registerListener` 把第一次覆盖了——只有最后一个传感器有回调。

### ★ 4.3 必须 hook `unregisterListener`

不 hook 的话，App 已经注销的 listener 还在被模块推送。后果：

- 收到不该收的回调 → 逻辑错乱
- listener 持有的 Activity 已销毁 → `NullPointerException` 或内存泄漏
- 传感器关了还在掉数据 → App 内部的「传感器已停」判断失效

注销有带 sensor 和不带 sensor 两种重载：带 sensor 的删单条，不带的删该 listener 名下全部。

### 4.4 三个派发循环

全部跑在**独立 `HandlerThread`** 上（`bg()`），不占 App 主线程：

| 派发 | 频率 | 内容 |
|---|---|---|
| 位置 | 1 Hz | 给捕获到的 `LocationListener` 调 `onLocationChanged` |
| 计步 | 1 Hz | `STEP_COUNTER`(type 19) 推累计步数；`STEP_DETECTOR`(type 18) 按步频推多次 |
| 加速度 | **50 Hz** | `ACCELEROMETER`(type 1) 推 `GaitEngine` 合成的波形 |

### ★ 4.5 为什么加速度必须 50 Hz

App 自己按约 66.7 ms（≈15 Hz）采样数峰。步态在 172 SPM ≈ **2.87 Hz**，一个步周期 348 ms。按 1 Hz 推送 → 一个周期内 0~1 个点 → **数不出峰 → 步频 0**。

50 Hz 时一个步周期有 ~17 个采样点，高斯峰的形状能完整还原，峰值可稳定检测。

### 4.6 `SensorEvent` 怎么造

`SensorEvent` 没有公开构造函数。反射路径：

```java
Constructor<?> ctor = SensorEvent.class.getDeclaredConstructor(int.class);  // 参数是 values 数组长度
Object ev = ctor.newInstance(values.length);
((float[]) fValues.get(ev)) → arraycopy
fSensor.set(ev, sensor);
fTs.setLong(ev, SystemClock.elapsedRealtimeNanos());
fAcc.setInt(ev, 3);
```

然后对 listener 调 `onSensorChanged(ev)`。

**性能注意**：50 Hz × N 个 listener，如果每次调用都做反射查找，就是每秒几百次 `getDeclaredField`。所以 `ctor` / `fSensor` / `fTs` / `fAcc` / `fValues` 在 `startDispatchers()` 里**预先查好缓存**，`onSensorChanged` 方法也在 `findMethod` 里 cache-friendly 地按 `(name, argc)` 找。

### 4.7 `findMethod` 为什么要找父类

listener 常常继承自 `SensorEventListener` 的抽象适配器（例如匿名类继承某个 Adapter）。`listener.getClass().getDeclaredMethods()` 只返回本类声明的方法，拿不到父类实现。

`findMethod` 沿 `getSuperclass()` + `getInterfaces()` 双向查找。

## 7. 轨迹引擎 `RouteEngine`

### 7.1 核心：时间 → 位置的纯函数

```java
static double[] positionAt(long nowMs) {
    double travelled = travelledMeters(nowMs);   // 沿路线累计里程
    // 按 cum[] 前缀和数组定位当前在哪个线段，再线性插值
}
```

关键性质：**无状态**。任意时刻 `t` 调 `positionAt(t)`，无论从哪个进程、哪个线程调，结果都一样。

为什么这很重要：目标 App 有多个进程（主进程 + pushservice），各自都会算位置/步数。如果依赖「逐帧累加」的状态，两边算出来必然对不上 → 破绽。纯函数天然一致。

### 7.2 路线：16 边形环 或 自定义折线

```java
static final class Route {
    final double[][] pts;    // 顶点
    final double[] cum;      // 前缀和累计距离
    final double total;      // 闭合周长
    final double centerLat, centerLng;
}
```

- `cum[i]` 是走到第 i 个顶点的累计距离，用来 O(log n) 定位分段
- `total` 加上最后一顶点回起点的距离，实现**无限循环**
- 所有字段 `final`：换路线时整体替换引用，读侧无需加锁

`buildRing()` 生成 16 边形：用 `radiusDeg` 直接加在纬度上，经度方向除以 `cos(lat)` 补偿。16 边形对 39 m 半径来说，"多边形感"完全无法察觉（相邻顶点间距 15 m，而定位每 1 s 只走 2.4 m）。

### 7.2b 坐标系：配置存 GCJ-02，路线跑 WGS-84

这是本项目最后修掉、也是最容易漏的一处。`Route` 里的所有点**必须是 WGS-84**，而配置文件里存的是 **GCJ-02**，两者的桥在 `applyConfig()` 第一段：

```java
boolean needConvert = !unset;          // 兜底占位常量本身是 WGS，不用转
if (cfg.path != null && cfg.path.size() >= 2) {
    double[][] gcjPts = cfg.path.toArray(new double[0][]);
    pts = needConvert ? Geo.pathGcjToWgs(gcjPts) : gcjPts;
    ...
} else {
    if (needConvert) { double[] w = Geo.gcjToWgs(lat, lng); lat = w[0]; lng = w[1]; }
    pts = buildRing(lat, lng, degreesForRadius(cfg.radiusM));  // 环在 WGS 下现生成
}
```

三个要点：

1. **路径点逐点转换**，不抽稀 —— 角点被平滑掉会让 App 判「瞬移」。
2. **环在转换后的中心上现生成**，生成的顶点已经是 WGS-84，不能对它们二次转换。
3. **兜底占位常量是 WGS-84**，`unset` 时必须跳过转换，否则那 370 米会加到一个本来就虚假的点上。

反方向在高德那一侧：`AMapLocation` 的约定是 GCJ-02，所以 `getLatitude()`/`getLongitude()` hook 和 `fillAmapLocation()` 里的 `mLatitude`/`mLongitude` 都要把 WGS-84 转回 GCJ-02（`RunSpoofModule.amapWgsToGcj()`）。**漏掉这一侧，地图上的轨迹会单独偏 370 米**，而位置判区反而是对的 —— 这种「一半对一半错」最难查。

`Geo.gcjToWgs()` 用迭代逼近（8 轮），残差 < 0.01 米；只在换路线时算一次，CPU 开销可忽略。

### 7.3 配速/朝向/步数全部由同一个 `t` 推导

```java
travelledMeters(nowMs)  → 位置
currentSpeed(nowMs)     → getSpeed
bearingAt(nowMs)        → getBearing
stepsFloat(nowMs)       → 步数
```

四个值同源。这是**服务端 `SpeedPerTenSec` 校验能过的根本原因**：速度序列积分出来就是走过的距离，跟坐标序列完全一致，不存在「坐标跳变但速度没变」的矛盾。

### 7.4 配置热重载

```java
private static void maybeReloadConfig() {
    if (now - lastCfgCheck < 3000) return;      // 3 秒最多查一次
    String sig = ConfigStore.signature();        // 内容指纹
    if (sig.equals(lastCfgSig)) return;
    lastCfgSig = sig;
    applyConfig(ConfigStore.read(), true);       // true = 路线从头开始
}
```

用**内容指纹**而不是文件 mtime：换成 remote preferences 后没有 mtime。而且从 UI 保存到注入侧读到，走的是跨进程 SharedPreferences 回调，中间有几百毫秒延迟，3 秒轮询足够。

改配置时 `startMs` 重置 → 轨迹从头开始。这是有意的：换了中心点还接着旧进度会瞬间瞬移几百米。

## 8. 步态引擎 `GaitEngine`

### 8.1 核心思路：解析可积

所有噪声都用**有限个正弦叠加**（`SmoothNoise`），因为正弦的积分有解析解：

```
value(t)   = Σ wᵢ·sin(2πt/Tᵢ + φᵢ)
integral(t) = Σ (wᵢ·Tᵢ/2π)·(cos(φᵢ) − cos(2πt/Tᵢ + φᵢ))
```

于是「累计步数」「累计距离」都能**直接算**，不需要逐帧累加。

这是整个设计里最关键的一点。如果改用随机游走或 Perlin 噪声：

- 累计量只能靠每帧累加
- 主进程和 pushservice 进程各自累加 → 结果不同 → App 内部对不上 → 异常
- 时间回退/重放 → 状态崩坏

### 8.2 波形表：零均值是硬要求

```java
private static double[] zeroMeanTable(ShapeFn shape) {
    // 256 点采样 → 减去均值 → 查表
}
```

真实加速度计在**一个完整步态周期内的平均值必须恰等于重力**。不是「大约等于」，是必须。否则长时间积分会累积出「设备持续加速」的破绽（可以想象成一段持续 30 分钟的自由落体）。

步行波形（4 个高斯叠加）：

```
+1.00 · bump(0.00, 0.045)     脚跟着地冲击（尖峰）
−0.45 · bump(0.13, 0.070)     支撑期回落
+0.55 · bump(0.42, 0.090)     蹬地第二峰
−0.65 · bump(0.72, 0.130)     摆动期低谷
```

跑步波形（3 个）：

```
+1.00 · bump(0.00, 0.035)     更尖锐的落地冲击
+0.55 · bump(0.16, 0.090)     支撑期主峰
−0.85 · bump(0.62, 0.180)     腾空期接近失重
```

### 8.3 步行 ↔ 跑步用 `smoothstep` 过渡

上游用 `speed >= 2.2` 硬切，振幅从 `2.0 + 1.0×2.2 = 4.2` 直接跳到 `6.0 + 1.5×2.2 = 9.3`。真机不可能这样——那是 2 倍振幅突变。

```java
double runW = smoothstep(1.8, 2.8, speed);
double amp = walkAmp * (1 - runW) + runAmp * runW;
```

1.8~2.8 m/s 之间平滑过渡。注意默认速度 2.4 正好**落在这个过渡带中间**（`runW ≈ 0.5`）——这是刻意的，让默认参数下波形是步行和跑步的自然混合，不是典型跑步那种极尖锐的冲击。

### 8.4 五项真实感改进

| # | 改进 | 实现 |
|---|---|---|
| 1 | 步行/跑步平滑混合 | `smoothstep(1.8, 2.8, speed)` |
| 2 | 左右腿 1~3% 不对称 | `legAsymmetry = 0.01 + 0.02*rand`，奇偶步分别放大/缩小 |
| 3 | 步时抖动 CV≈1.5% | 按步索引的 `strideTimeNoise` 累积积分，幅度 0.3% |
| 4 | 传感器量化 + 慢零偏 | `quantize()` 到 `0.0012 m/s²`；`biasDrift` 60~600 s 周期，三轴独立相位 |
| 5 | 疲劳衰减 | 12 分钟后启动，`tanh` 过渡，最多 −4% |

第 4 项的量化值 `0.0012` 不是随手写的：典型 MEMS 加速度计量程 ±16g、16 bit → `16×9.81/32768 ≈ 0.0048`；±8g、16bit → `0.0024`。取 `0.0012` 对应 ±4g / 16 bit，是运动手环类设备的常见配置。

每次读数还叠加 `N(0, 0.06)` 白噪声，因为真实 MEMS 输出一定有底噪。

### 8.5 `hashUnit`：确定性伪随机

```java
static double hashUnit(long seed, long n) {
    long x = seed ^ (n * -0x61c8864680b583ebL);
    x = (x ^ (x >>> 33)) * -0x4f4e7a1d3b6a8f31L;   // 实际是 splitmix64 系列
    ...
    return (double)(x >>> 11) / (double)(1L << 53) * 2 - 1;
}
```

用途：第 N 步的力度抖动。关键性质是**由 `(seed, n)` 唯一决定**——主进程和 pushservice 进程算第 1234 步的力度，结果完全一样。

不能用 `Math.random()` 或普通 `Random`：那是**有状态**的，两个进程从同一个 seed 出发，但如果调用次数不同（比如一个多推了几帧），后面全部错开。

`(x >>> 11) / 2^53` 是标准做法：取 double 尾数 52 位，映射到 `[0,1)`，再 `×2−1` 到 `[-1,1)`。保证均匀且不产生大于 1 的值。

## 9. 配置通道 `ConfigStore`

### 9.1 最终方案：`/data/local/tmp` 文件通道

```
UI 进程（模块自己的 APK，uid=u0_aNN）
  写 /data/local/tmp/runspoof_route.txt（普通文本，key=value）
      ↓
注入进程（目标 App 的 uid=10052）
  读同一个文件 → 解析成 Config
```

这是**两种 uid 都能看见的唯一位置**。代价是：`/data/local/tmp` 的权限是 `drwxrwx--x shell shell`（**0771**），other 只有进入权限、没有写权限，所以**普通 App 建不了这个文件**。

解决方式：由用户用 adb 先建好并放开权限。

```bash
adb shell "touch /data/local/tmp/runspoof_route.txt; chmod 666 /data/local/tmp/runspoof_route.txt"
```

文件建好之后，模块界面就能一直往里写（写已存在的文件不需要目录写权限，文件本身 666 就够）。

### ★ 9.2 为什么不能用别的通道

这两条都是**实际试过、都失败**的：

| 通道 | 失败原因 |
|---|---|
| libxposed remote preferences | LSPosed 2.2.1 + API 102 上 `getRemotePreferences()` **调用成功但返回空表**，不报错、不打日志，静默失效。查 `/data/adb/lspd/config/modules_config.db` 的 `module_configs` 表发现我们的模块从没写进去过 |
| 直读模块的 `shared_prefs/runspoof.xml` | Android 10+ 的 **per-app data isolation**：注入进程的 mount namespace 里 `/data/data` 是 tmpfs，只挂它目标 App 自己那一份，看不到模块的目录 |

把 prefs 文件 `chmod 644`、目录 `chmod 711`、`restorecon` 都试过，全部无效——因为根本不是权限问题，是**文件在那个 namespace 里不存在**。

### 9.3 为什么不用 root

思路上的诱惑是「让注入进程 `su` 一下去 root 读文件」，但这会把模块的权限要求从「LSPosed 模块」提升到「必须 root 且每次弹授权」，而且 `su` 在 App 进程里调用的兼容性极差。

`/data/local/tmp` 是内核对所有 uid 都可见的真实目录，不需要任何特权——**只需要用户一次性建个文件**。这是成本最低的方案。

### 9.4 文件格式

```
centerLat=<你的中心纬度>
centerLng=<你的中心经度>
radiusM=39.0
speedMps=4.2
cadenceSpm=172.0
point=<lat>,<lng>
point=<lat>,<lng>
...
```

写的时候 `path` 有两种形式：

- UI 保存时写成逐行 `point=lat,lng`
- 手工 / 早期版本写成一行 `path=lat,lng;lat,lng;...`

`Config.parse()` 两种都认（`case "path"` 走 `setPathString()`）。

### 9.5 内容指纹

```java
static String signature() {
    // 文件通道下直接返回 "file:" + lastModified + ":" + length
}
```

`RouteEngine` 每 3 秒比一次指纹，变了才重新 apply。这样 UI 上点「保存」后最多 3 秒生效，用户感觉是即时的。

用 `lastModified + length` 而不是内容哈希：文件才几百字节，比对 mtime 更便宜，且足够检测变化。

### 9.6 注入侧读不到时的表现

如果用户漏了第 9.1 节那条 `touch` 命令，模块会一直用代码里的默认值 `centerLat=0.0, centerLng=0.0`。

界面上看不出来——编辑器里画得好好的，但目标 App 里跑的是默认位置。**唯一的证据是 logcat**：

```
I LSPosedFramework: system hooks installed, route=384m, center=0.0,0.0
```

`center=` 等于默认值就是没读到。所以 v23 起 UI 保存失败会直接弹框：

```
配置没能生效
请在电脑上执行：
adb shell "touch /data/local/tmp/runspoof_route.txt; chmod 666 /data/local/tmp/runspoof_route.txt"
```

## 10. 地图选点 UI

`MapPickerActivity`：一个 WebView 里塞纯 HTML/CSS/JS 的地图，通过 `@JavascriptInterface` 双向通信。

### ★ 为什么不用 Leaflet

旧版从 `unpkg.com` 拉 Leaflet。国内网络下 unpkg 经常超时 → **地图一片空白，只有按钮**。

现在自带极简瓦片地图实现：

- 瓦片源用高德（`webrd0{1-4}.is.autonavi.com`），国内可达
- 手写拖拽/缩放（`touchstart`/`touchmove`/`wheel`）
- 点击换算成经纬度，标点

代码量不大，但**不依赖任何外部 CDN**，断网也能出图（瓦片加载不出来时至少有网格和坐标）。

### ★ 三个设计上的硬要求

这三条都是第一版做完后发现不能用才补的：

1. **必须画线，不只是画点**
   第一版只在点击处画小圆点。点了 20 个点还是看不出形状，用户根本没法判断自己画的是不是跑道。现在画实心 polyline + 自动闭合虚线 + 编号顶点。

2. **拖动视野不能改数据**
   第一版 `render()` 永远把视野锁在 `cLat/cLng`，而平移又直接改这两个变量——**拖一下地图就把路线中心挪走了**。实测拖了一次偏差 1.7 km。
   现在拆成两套变量：`vLat/vLng`（视野）与 `cLat/cLng`（路线中心），平移只改前者。

3. **编辑与保存分离**
   第一版点一下地图就 `writeUi()` 落盘，没有撤销，误触直接改掉已保存配置。
   现在改动只在内存，必须按「保存配置」才写盘，另有 50 步撤销栈。

### 交互

| 操作 | 效果 |
|---|---|
| 点地图空白处 | 追加一个路径点 |
| 拖动已有顶点 | 微调该点位置 |
| 长按顶点 600ms | 删除该点 |
| 拖动地图 | **只移动视野**，不动路线中心 |
| 定中心 → 点地图 | 把该点设为路线中心（红色三角） |
| 跑道圈 | 按当前中心 + 半径生成 24 点标准跑道（两直道 + 两半圆） |
| 撤销 | 回退一步（50 步） |
| 清空 | 清掉路径 |
| 保存配置 | 才真正写盘 |
| 恢复默认 | 恢复内置默认值 |

`alignCenterToPath()`：保存时如果路径 ≥2 点，**自动把中心点设成路径顶点均值**。因为实测用户经常直接点「跑道圈」而不按「定中心」，导致路径在场地 A、中心还在场地 B，差 1.7 km。

### 参数输入与钳制

半径 / 速度 / 步频三个输入框带常驻标签（旧版只有 hint，填了值标签就消失，界面上只剩三个裸数字）。

超范围的值在 `Config.clamp()` 里被**自动钳制**：

| 参数 | 钳制范围 | 依据 |
|---|---|---|
| `speedMps` | 1.9 ~ 5.4 | 配速 8'46" ~ 3'05"，两端留余量（真实区间按本校规则调整） |
| `cadenceSpm` | 45 ~ 290 | 与速度自洽的常见人类步频 |
| `radiusM` | 5 ~ 200 | 太小绕得极密、太大溢出围栏 |

NaN / Infinity 回落到默认值。手填一个出界值跑完也是白跑，静默修正比让成绩作废好。

## 11. 时序总览

一次计分跑的完整数据流：

```

      onPackageLoaded → ConfigStore.attach → RouteEngine.ensureInit
      → 7 类 hook 全部挂上 → startDispatchers

t=1s  App 注册 LocationListener

      模块 dispatcher 每秒推 1 次伪造 Location

t=1s  App 注册加速度计 listener
      hook 捕获，模块 50Hz 推 GaitEngine 波形
      App 数峰 → 步频 ≈ 172 SPM

t=1s  App 请求高德定位
      AMapLocationClient startLocation
      1 秒后模块对捕获的 AMapLocationListener 推 fillAmapLocation 好的对象
      App 拿到坐标/速度 → 地图上开始移动

      坐标序列积分 = 24 m，速度积分 = 24 m → 自洽

t=…   跑满你校要求的里程上限后建议停止
      （继续推位置会被判超量，具体上限看你 App 规则页）

全程  每 3 秒检查配置指纹，UI 改了立刻生效
```

## 12. 代码里不该动的几处

如果后续想改这个项目，下面这些**建议原样保留**，每一处都对应一个已修复的 bug：

| 位置 | 原因 |
|---|---|
| `hookOne` 的继承链遍历 | 否则父类方法静默漏 hook |
| `requestLocationUpdates` 里的 `chain.proceed()` | 否则 App 永远收不到位置 |
| `getLatitude` 用 `timeOf(this)` | 否则 `distanceTo` 恒 0 |
| 不拦 `Location` setter | 否则 native 读字段恒 0 |
| `hookSingleGnssCallback` 的 `proceed(Object[])` | 否则 Android 15 上抛异常吞掉真实回调 |
| `stepListeners` 的 `(listener,sensor)` key | 否则多传感器互相覆盖 |
| `unregisterListener` 的 hook | 否则已注销的 listener 仍被推送 |
| `SmoothNoise` 的正弦叠加（不是随机游走） | 否则跨进程累计量不一致 |
| `zeroMeanTable` | 否则长时间积分累积出「持续加速」 |
| `build.ps1` 末尾的 APK 条目校验 | 否则 `META-INF/xposed` 位置错了发现不了 |
