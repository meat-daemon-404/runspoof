# 05 · 模拟器与虚拟化

**先说结论：这个项目建议用真机。**

下面这些内容仍然是值得写的，因为「LSPosed 在模拟器里起不来」是一个很典型的排查场景，而且它的**真实成因和大多数人以为的不一样**。

---

## 1. 症状

用 MuMu 模拟器（Android 12/13 镜像）+ KernelSU + LSPosed 2.2.1：

```
LSPosed 管理器：模块列表正常显示，作用域能勾
但所有模块都不生效
lspctl --json status → "systemServerRequested": false
```

看进程：

```bash
adb shell su -c 'ps -A | grep lspd'
```

`lspd` 进程**存在**，但过一会就没了。抓崩溃日志：

```
F libc    : Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR)
F DEBUG   : pid: ..., tid: ..., name: lspd
F DEBUG   : signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x314
F DEBUG   :     x0 ... x1 ...
F DEBUG   :     rbp 0x314  rsp 0x314  rip 0x314
```

`rip = rbp = rsp = 0x314` 这个特征很特别——**三个寄存器同时变成一个非地址值**。正常栈破坏很少三寄存器同步坏。

---

## 2. 第一层原因：Hyper-V / HVCI 让模拟器退化

宿主机检查：

```powershell
# Hypervisor 是否存在
(Get-CimInstance Win32_ComputerSystem).HypervisorPresent
# True

# HVCI（内存完整性）状态
reg query "HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity" /v Enabled
# Enabled = 1
```

Hyper-V 占用了 **VT-x**，MuMu（底层是 VirtualBox）拿不到硬件虚拟化，于是退化：

```
VBox.log:
  00:00:0x VT-x is not available (VERR_VMX_NO_VMX)
  00:00:0x Snail execution mode is active!
```

**Snail 模式**是 VirtualBox 的纯软件 CPU 模拟。它会把 CPU 报告成一台很老的机器：

```
adb shell cat /proc/cpuinfo | grep "model name"
# model name : Intel(R) Pentium(R) CPU N3530 @ 2.16GHz
```

N3530 是 2014 年的 Silvermont 架构。**LSPosed 的 native 桥接代码在 Snail 模拟下走错了路径，踩坏了栈**，所以出现 `rip=0x314`。

### 修正方式

```
Windows 安全中心 → 设备安全性 → 内核隔离 → 内存完整性 → 关闭
或注册表：
reg add "HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity" /v Enabled /t REG_DWORD /d 0 /f
```

重启。重启后 `HypervisorPresent` 可能仍为 True（其他 Hyper-V 功能占用），但 HVCI 关了通常就够。

---

## 3. 第二层原因（真正的主因）：双 `lspd` 竞争

关掉 HVCI 后症状**缓解但没根治**——有时能起来，有时不能。继续挖，发现每次开机后：

```bash
adb shell su -c 'ps -A | grep -c lspd'
# 2
```

**两个 lspd 同时在跑**。

### 为什么会跑两次

KernelSU 的模块 `service.sh` 在开机时被触发了**两次**（具体机制和 KernelSU 版本、`post-fs-data` 阶段的行为有关）。每次触发都启动一个 `lspd`。

两个 `lspd` 抢着建立 system_server 的桥接：

- 先到的占住 socket / 共享内存
- 后到的连不上 → 走到错误路径 → SIGSEGV
- 后到的崩了会留下脏状态，先到的那一个也可能被带崩

**Snail 模式让这个竞争的窗口大幅拉长**（软件模拟的时序不稳），所以必输。关掉 HVCI 恢复硬件虚拟化后窗口变短，通常能赢——但仍是竞态，不保证。

### 根治：boot_id 单实例守卫

在 `/data/adb/modules/zygisk_lsposed/service.sh` 开头加：

```sh
#!/system/bin/sh

# 同一个 boot 内只跑一次。
# KernelSU 有时会在开机阶段触发两次 service.sh，
# 两个 lspd 抢桥接，后起的必崩（rip=0x314），先起的也可能被带崩。
BOOT_ID=$(cat /proc/sys/kernel/random/boot_id)
GUARD=/data/adb/lsposed_boot_guard

if [ -f "$GUARD" ] && [ "$(cat "$GUARD")" = "$BOOT_ID" ]; then
    exit 0
fi
echo "$BOOT_ID" > "$GUARD"

# ... 原有启动逻辑保持不变 ...
```

`/proc/sys/kernel/random/boot_id` 每次开机变一次，用它判断「是不是同一个 boot」最准确。

> **注意**：原 `service.sh` 末尾如果有 `&`，必须保留。`&` 是后台启动语义，删了会导致开机卡在等 `lspd` 前台退出。

### 验证

```bash
adb shell su -c 'ps -A | grep -c lspd'
# 1
adb shell su -c 'cd /data/adb/modules/zygisk_lsposed && ./lspctl --json status'
# "systemServerRequested": true
```

## 4. 第三层：模块文件是否被改过

排查过程中很容易忽略：**你手上的 LSPosed 包可能不是官方的**。

正确做法是逐字节比对：

```bash
# 下载官方包 https://lsposed.zip，解压
# 对比 daemon.apk / manager.apk 的 sha256
adb shell su -c 'sha256sum /data/adb/modules/zygisk_lsposed/daemon.apk'
adb shell su -c 'sha256sum /data/adb/modules/zygisk_lsposed/manager.apk'
```

和官方 zip 内同名文件比。实测这一步能排除掉大量「以为是环境问题，其实是二进制被换过」的情况。

## 5. 第四层：odex 陈旧

系统升级过、或者很久没重启，`daemon.odex` 可能和当前 ART 版本不匹配：

```bash
adb shell su -c 'ls -l /data/adb/modules/zygisk_lsposed/oat/*/'
```

强制重编译：

```bash
adb shell su -c 'rm -f /data/adb/modules/zygisk_lsposed/oat/*/daemon.odex'
adb shell su -c 'dex2oat64 \
    --dex-file=/data/adb/modules/zygisk_lsposed/daemon.apk \
    --oat-file=/data/adb/modules/zygisk_lsposed/oat/x86_64/daemon.odex \
    --instruction-set=x86_64'
```

然后重启。

## 6. MuMu 的假 GPS 也不可靠

即使 LSPosed 起来了，MuMu 的定位还有两个问题。

### 6.1 固定偏移

```powershell
MuMuManager.exe adb -v 0 shell
# MuMuManager.exe tool location -v 0 --latitude <纬度> --longitude <经度>
```

设了坐标，模拟器里定位出来的却是：

```
lat <纬度 - 0.00316>
lon <经度 + 0.00782>
```

**这是一个与目标坐标无关的固定偏移**（纬度偏南约 0.00316°、经度偏东约 0.00782°，量级约 350 米和 780 米）。反向补偿（设成 `lat + 0.00316, lon - 0.00782`）后误差约 **11 米**——仍不足以让轨迹稳稳落进半径 39 m 的有效区域中心（勉强够，但边缘会抖出去）。

### 6.2 重启后失效

`nemu` 的 last location 在模拟器重启后变成 `null`，假 GPS 直接不工作。App 会提示「无法定位」。

### 结论

**不要让模块依赖模拟器提供的 GPS。** 模块必须能独立产出位置——这就是 `RouteEngine` 存在的理由之一。它不读任何系统定位，纯靠时间函数算坐标。

## 7. 真机 vs 模拟器

| 维度 | 真机 | 模拟器（MuMu/雷电/夜神） |
|---|---|---|
| LSPosed 稳定性 | ✅ 正常 | ⚠️ 依赖宿主机虚拟化配置 |
| 系统版本 | 真实 | VirtualBox 魔改，可能和 AOSP 有差异 |
| 传感器数据 | 真实硬件 | 模拟层，可能有额外噪声 |
| 定位 | 真实 GNSS | Snail 模式下基本不可用 |
| 加速度计 | ✅ | ⚠️ 可用，但采样率/量化可能不标准 |
| 反作弊检测 | 可能检测到 root | 可能检测到模拟器 |
| **推荐度** | **✅** | 仅用于「能不能装上、hook 有没有挂上」的冒烟测试 |

### 建议的验证路径

1. **模拟器**：只验证「APK 装得上、LSPosed 认得出、logcat 里 `all hooks installed`」
2. **真机**：验证「跑起来数据对不对」

这个分工能省掉大量在模拟器上死磕虚拟化的时间。

---

## 8. 如果一定要用模拟器

按这个顺序做，别跳步：

1. 关 HVCI，重启
2. 确认 KernelSU 里 Zygisk Next 已启用，重启
3. 部署 `boot_id` 守卫脚本，重启
4. `lspctl --json status` 看 `systemServerRequested: true`
5. 装模块，勾作用域
6. `lspctl --json modules` 确认模块在列表里
7. 强杀目标 App，重启，看 `logcat -s RunSpoof:V`
8. 生效后才去管「数据对不对」

**任何一步没过，后面全部无意义。** 在这个项目里，80% 的「模块不生效」都出在第 1~4 步。

## 附：宿主机环境速查

```powershell
# Hyper-V 是否启用
Get-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All | Select State

# 虚拟化是否被占用
(Get-CimInstance Win32_ComputerSystem).HypervisorPresent

# HVCI 状态
reg query "HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity" /v Enabled

# 已启用的 Windows 功能里和虚拟化相关的
Get-WindowsOptionalFeature -Online | Where-Object {
    $_.FeatureName -match 'Hyper|Virtual|Sandbox|WSL|Containers'
} | Select FeatureName, State

# MuMu 的 CPU 报告（连接后）
adb shell cat /proc/cpuinfo | Select-String "model name"
```

`/proc/cpuinfo` 报出老 CPU 型号（如 N3530、QEMU Virtual CPU、VirtualBox）就是 Snail 模式的铁证。

---

## 一句话

模拟器上的 LSPosed 问题，**90% 是宿主机的虚拟化配置**，而且真正的触发机制往往是**开机时的双实例竞争**——这个结论花了很久才挖出来，因为它和「虚拟化」这个表面原因混在一起，关掉 HVCI 只是把概率从「必崩」降到「有时不崩」。
