## 第 0 步 · 先搞清楚这东西在做什么

很多人对这类模块的第一印象是「改个 GPS 坐标」。**只改坐标是没用的**，因为校园跑类 App 判定的是一整套互相关联的输入：

| 它验什么 | 只改坐标会怎样 |
|---|---|
| 位置来源 | 走**系统 `LocationManager`**，`RequestLocationUpdates` 注册后由系统持续回调。只改一次坐标不行，得接管整条回调链 |
| 里程 | 用相邻两点的 `distanceTo()` 累加。两点时刻相同距离就是 0 |
| 步数 | 读**加速度计波形数峰**（采样约 15 Hz）。1 Hz 推一下还原不出步态 |
| 配速 | 服务端用 10 秒段速度序列**独立重算**，和你上报的对不上就判异常 |
| 有效性 | 原生库里有一套点位评分，缺项就无效 |
| 环境 | GNSS 卫星数、WiFi、基站、mock 标记，任一露馅就进风控 |

所以这个模块做的事是：**生成一套时间上连续、物理上自洽的输入**——轨迹按时间推进，速度反推步频，加速度波形按步频合成，GNSS/WiFi/基站补齐，反作弊标记清理掉。

下面的步骤就是把这套东西装到位。

## 第 1 步 · 确认你的设备能不能用

**先明确一件事：这个项目建议用真机。**

原因很实际：模拟器要走虚拟化，宿主机开了 Hyper-V / HVCI 之后 MuMu 之类的模拟器会退化到纯软件模拟（VirtualBox 的 Snail 模式），LSPosed 的 native 桥接在这种模式下会崩。这一条我们踩过，完整记录在 [05-模拟器与虚拟化](05-模拟器与虚拟化.md)。如果你只有模拟器，先看那篇。

### 硬性条件

| 项目 | 要求 | 为什么 |
|---|---|---|
| Android 版本 | **13 及以上**（模块 targetSdk 34） | 大量反射字段名按 14/15 的 AOSP 写的 |
| root | **必须**，KernelSU 或 Magisk | LSPosed 要有 root 才能挂 zygote |
| Zygisk | Zygisk Next / ReZygisk | LSPosed 2.2.x 依赖它注入 |
| LSPosed | **2.2.1 及以上** | 老版本不认新格式模块声明 |
| 目标 App | 运动世界校园 `com.zjwh.android_wh_physicalfitness` | 其它校园跑 App 未适配 |

### 自查

手机上装个终端（或用 `adb shell`），确认：

```bash
# 1. 有没有 root
id          # 期望看到 uid=0(root)
# 或者 KernelSU 环境
ls /data/adb/ksu

# 2. LSPosed 起没起来
ls /data/adb/lspd
```

`id` 还是普通 uid、或者 `/data/adb/lspd` 不存在，就停在根上先解决 root 和 LSPosed，后面全做不了。

> **注意**：有些设备的 `su` 不在 PATH 里，`su -c id` 会报 `inaccessible or not found`，但 `adb root` 或 KernelSU 管理器里其实是有 root 的。以 KernelSU/Magisk 管理器里的状态为准，别被 `su: not found` 误导。

## 第 2 步 · 装 root、Zygisk、LSPosed

这一段的顺序不能颠倒：**root → Zygisk → LSPosed**，每一层都依赖上一层。

1. **刷 KernelSU 或 Magisk**
   解锁 bootloader，打补丁 boot.img，刷入。这一步因机型而异，不在本文范围。

2. **装 Zygisk 提供者**
   LSPosed 2.2.x 不再自带 Zygisk，需要单独装 **Zygisk Next**（或 ReZygisk）模块，在 KernelSU/Magisk 管理器里刷入后重启。

3. **装 LSPosed**
   下载 LSPosed 2.2.1+ 的 zip，在管理器里刷入，重启。

重启后验证：

```bash
ls /data/adb/lspd            # 期望有目录
```

打开 LSPosed 管理器，能看到模块列表页（此时是空的），说明框架活了。

> **踩坑预告**：如果 LSPosed 管理器能打开但模块装上去不识别，先看 [01-环境准备](01-环境准备.md) 里「LSPosed 起不来」那一节。最常见的原因是开机时 KernelSU 的 `service.sh` 被触发了两次，起了两个 lspd 互相抢，日志里能看到两个不同 pid。根治办法是给 `service.sh` 加一个按 `boot_id` 判断的单实例守卫，完整脚本贴在 [01-环境准备](01-环境准备.md) 的「6.2 双 lspd 竞争」一节。

## 第 3 步 · 让 LSPosed 认识这个模块

**这一步是整条链里最容易踩坑的地方，值得单独讲。**

传统的 Xposed 模块用 `META-INF/xposed/module.prop`（或者更老的 `assets/xposed_init`）声明自己。LSPosed 2.2.1 之后改成了新格式，用一套 `META-INF/xposed/` 目录，并且：

> **`META-INF/xposed/` 必须在 APK 的根目录，不能在 `assets/` 下面。**

这不是风格问题，是硬性的。判断依据是 LSPosed 读 APK 时只扫根级 `META-INF/xposed/`，放 `assets/META-INF/xposed/` 它会当成普通资源文件忽略掉，表现就是——**模块装得上，但 LSPosed 列表里压根不出现**。

### 三个文件

| 文件 | 内容 | 作用 |
|---|---|---|
| `module.prop` | `minApiVersion=101`<br>`targetApiVersion=102` | 声明用的 API 版本。101 是 LSPosed 2.2.1 支持的最低新格式 |
| `java_init.list` | `com.qf.runspoof.RunSpoofModule` | 模块入口类，LSPosed 加载时反射调用 |
| `scope.list` | `com.zjwh.android_wh_physicalfitness` | 默认作用域，安装后自动勾上目标 App |

如果自己打包，检查一下 APK 里到底有没有：

```bash
unzip -l RunSpoof.apk | grep xposed
```

期望输出（**路径开头就是 `META-INF/`，前面没有 `assets/`**）：

```
META-INF/xposed/module.prop
META-INF/xposed/scope.list
META-INF/xposed/java_init.list
```

如果看到的是 `assets/META-INF/xposed/...`，说明打包方式错了。Windows 上用 `aapt2 -A assets` 打包必定踩这个坑——`aapt2` 会把路径分隔符写成反斜杠，LSPosed 认不出来。正确做法是用 `jar uf` 手动加，详见 [02-构建与打包](02-构建与打包.md)。

## 第 4 步 · 装模块并激活

### 4.1 安装 APK

从 [Releases](https://github.com/sun-zihang/runspoof/releases) 下载最新的 `RunSpoof-v*.apk`，直接安装。

```bash
adb install -r RunSpoof-v41.apk
```

如果之前装过别的版本、报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`，说明签名不一致，先卸再装：

```bash
adb uninstall com.qf.runspoof
adb install RunSpoof-v41.apk
```

> 换签名会丢掉模块自己的数据（SharedPreferences），但**不会**丢掉 `/data/local/tmp` 下的配置文件。所以升级后路线还在，这也正是配置文件放在那里的好处之一。

### 4.2 在 LSPosed 里启用

打开 LSPosed 管理器 → **模块** → 找到 **RunSpoof** → 勾选启用。

### 4.3 设置作用域

在同一页点进模块，**作用域**里只勾 **运动世界校园**。

这一步别贪多。作用域开大了会让模块注入到一堆无关进程，既浪费内存也容易出奇怪问题。默认的 `scope.list` 已经写好了目标包名，正常情况下装完就是对的。

### 4.4 命令行方式（可选）

嫌点界面麻烦，可以直接用 `lspctl`：

```bash
# 启用（--user 必须带，0 是主用户）
/data/adb/ksu/bin/lspctl module enable --json --user=0 com.qf.runspoof

# 设作用域
/data/adb/ksu/bin/lspctl scope set --json --user=0 com.qf.runspoof com.zjwh.android_wh_physicalfitness
```

返回 `{"ok":true,...}` 就是成功。

### 4.5 重启目标 App

```bash
adb shell am force-stop com.zjwh.android_wh_physicalfitness
```

然后重新打开。模块声明了 `autoHotReload=true`，正常改完配置不用重启手机。

## 第 5 步 · 建配置文件（★ 最容易漏的一步）

**这一步不做，后面画路线全部白费。** 所以放在画路线之前讲。

### 为什么需要手动建文件

模块的配置要在**两个不同 uid 的进程**之间传递：

- **编辑器**（`com.qf.runspoof`）跑在模块自己 uid 下，负责写
- **注入代码**（打进目标 App 的那部分）跑在**目标 App 的 uid**（如 `10052`）下，负责读

Android 10+ 有 per-app data isolation：注入进程的 mount namespace 里 `/data/data` 是个 tmpfs，**只挂载了目标 App 自己那一个目录**。所以注入侧看不到 `/data/data/com.qf.runspoof/shared_prefs/`——不是权限不够，是这个路径在它的视图里根本不存在。

框架自带的 remote preferences 在 LSPosed 2.2.1 + API 102 上返回的是空表，也不可用。

**唯一两边都看得见的地方是 `/data/local/tmp`。** 那里没有 data isolation，是个全局可读写目录。

但 `/data/local/tmp` 的权限是 `drwxrwx--x`（0771）、属主 `shell`，普通 app uid **不能在里面新建文件**，只能写已经存在且放开权限的文件。

所以这个文件必须由你自己先建好。

### 建文件

电脑连着手机，执行：

```bash
adb shell "touch /data/local/tmp/runspoof_route.txt; chmod 666 /data/local/tmp/runspoof_route.txt"
```

验证：

```bash
adb shell ls -l /data/local/tmp/runspoof_route.txt
```

期望：

```
-rw-rw-rw- 1 shell shell 0 ...
```

关键是三个 `rw`（666）——模块编辑器和目标 App 两个 uid 都要能写能读。

> **不需要 root**。`adb shell` 本身就是 `shell` 用户，而 `/data/local/tmp` 属主就是 shell，所以它能建文件。设备上开个终端 app 也可以，但那里面是 app uid，建不了。

> **为什么不用框架的 remote preferences**：它在 LSPosed 2.2.1 + API 102 上 `getRemotePreferences()` 调用**成功**但返回**空表**，不报错不打日志。查 `/data/adb/lspd/config/modules_config.db` 的 `module_configs` 表能看到我们的模块从没被写进去过。完整的排查过程见 [00-踩坑总览 D1](00-踩坑总览.md)。

### 忘记做的后果

模块界面按「保存配置」，会弹一个框告诉你「配置没能生效」，并把上面那条命令原样显示出来。跟着敲一遍再保存一次即可。

**以前这个失败是静默的**——界面显示「已保存」，实际只写进了模块自己的 SharedPreferences，注入侧读不到，于是你在目标 App 里发现位置压根不动，然后开始排查一堆不相干的东西。现在会明确报出来。

## 第 6 步 · 画自己的路线

打开「**RunSpoof 路线**」（桌面图标，或 `adb shell am start -n com.qf.runspoof/.MapPickerActivity`）。

打开后应该看到一张高德底图（这里的高德**只用来加载瓦片地图**，和定位链路无关），顶部一行信息，下面是参数栏和地图。

### 界面说明

```
┌─────────────────────────────────────┐
│ 中心 <你保存的中心点> ｜ 配速 3'58" ｜ 步频 172 │
├──────────┬──────────┬──────────┬──────────┤
│ 定中心   │  撤销    │  跑道圈  │   清空   │
├──────────┼──────────┼──────────┤
│ 半径(m)  │ 速度(m/s)│ 步频(SPM)│
│   39     │   4.2    │   172    │
├──────────┴──────────┼──────────┴──────────┤
│      保存配置        │       恢复默认       │
├─────────────────────┴──────────────────────┤
│ 路径 19 点 ｜ 绕一圈 384 米                  │
├────────────────────────────────────────────┤
│                                            │
│              地  图  区  域                 │
│                                            │
└────────────────────────────────────────────┘
```

### 基本操作

| 操作 | 效果 |
|---|---|
| **点地图空白处** | 追加一个路径点 |
| **拖动已有顶点** | 微调该点位置 |
| **长按顶点** | 删除该点 |
| **拖动地图** | 只移动视野，**不动**路线中心 |
| **定中心** → 点地图 | 把该点设为路线中心（红色三角） |
| **跑道圈** | 以当前中心 + 当前半径，一键生成标准跑道 |
| **撤销** | 回退一步（保留 50 步历史） |
| **清空** | 清掉所有路径点 |
| **保存配置** | **只有按这个才真正写盘** |

画布上实时显示：实心折线（你的路径）、虚线（自动闭合回起点）、编号顶点（起点绿色）、红色三角（路线中心），顶部显示「路径 N 点 ｜ 绕一圈 X 米」。

> **编辑过程不写盘。** 所有改动只在内存里，误触不会毁掉已保存的配置。只有点「保存配置」才落盘。

### 两条推荐路径

#### 方案 A：直接「跑道圈」

1. 把地图拖到你学校操场，双击放大地图
2. 点「**定中心**」，然后点一下跑道中央
3. 半径填 **39**（默认值）。这个半径生成出来绕一圈约 **398 米**，接近标准 400 米跑道
4. 点「**跑道圈**」——会生成一个 24 点的标准跑道形状（两条直道 + 两个半圆，不是正圆）
5. 点「**保存配置**」

24 个点、直道沿东西向、两个半圆在南北两端，这是按真实田径场的几何做的。正圆看着假，而且和真实跑道照片对不上。

#### 方案 B：手描一圈（想完全贴合真实跑道时用）

1. 「清空」
2. 沿着跑道内圈边缘，**顺时针**点一圈，每 20~30 米一个点（400 米跑道大约 15~20 个点）
3. 点「保存配置」

点数不是越多越好。太密会让轨迹抖动看着不自然，太疏（比如只有 4 个点）在弯道上会变成明显折线。**一圈 15~20 个点**是比较舒服的量。

### 中心点会自动对齐

路径一旦有 ≥2 个点，保存时会把**中心点自动设成所有路径点的几何平均**。

这是为了防止一种情况：你画路线的位置在 A，但中心点还停在很久以前设的 B，两者差一两公里。中心点参与界面显示和「恢复默认」，长期不一致会让人以为路线没生效。

想手动指定中心，就在保存**之前**按「定中心」。

## 第 7 步 · 调速度与步频

两个参数决定「跑多快」和「步频多密」。改完顶部会立刻显示换算结果，不用自己算。

### 速度（m/s）

**这个参数直接决定配速，配速决定成绩是否有效。**

**有效配速区间各校不同**（在你 App 的规则页里能查到）。换算关系是：

配速（分/公里） = 1000 ÷ 速度 ÷ 60

界面右边的「配速」会实时显示换算结果，不用自己算。模块允许的输入范围与对应配速：

| 速度 | 配速 | 说明 |
|---|---|---|
| 1.9 m/s | 8'46" | 输入下限 |
| 2.0 m/s | 8'20" | 走跑交替的慢速 |
| 2.4 m/s | 6'57" | **默认值**，慢跑姿态最稳 |
| 2.75 m/s | 6'04" | 慢跑 |
| 3.0 m/s | 5'33" | 正常慢跑 |
| 3.5 m/s | 4'46" | 较快 |
| 4.0 m/s | 4'10" | 快跑 |
| 4.2 m/s | 3'58" | 偏快，起步阶段容易被标红 |
| 5.4 m/s | 3'05" | 输入上限 |

> 填了超出 1.9 ~ 5.4 的值会被自动钳制。**不要贴着自己学校的区间上下限填**——上下限附近任何一次瞬时抖动都可能越界。

模块把可调范围钳在 **1.9 ~ 5.4**，两端各留了一点余量，避免压线被浮点误差判出界。

**建议用 2.4 ~ 3.0**。数值越靠区间中段，服务端重算时越不容易被判异常；贴着 3 分或 9 分的边界，一点点计算误差就可能落到区间外。

超范围的值保存时会被**自动钳制**到边界，不报错。手填一个 9.9，存进去是 5.4。

### 步频（SPM）

每分钟步数。须落在你校的步频有效区间，模块钳在 **45 ~ 290**。

步频和速度之间要自洽——配速快、步频还低，说明步幅大得离谱，服务端会看出来。模块内部按 `步幅 = 速度 ÷ 步频 × 60` 反推，界面上实时显示。

| 速度 | 步频 172 时步幅 | 合理性 |
|---|---|---|
| 2.4 m/s | 0.84 m | 慢跑步幅，正常 |
| 3.0 m/s | 1.05 m | 正常跑步 |
| 4.2 m/s | 1.47 m | 大步快跑，偏大但可能 |
| 5.4 m/s | 1.88 m | 太大了，不自然 |

**默认 172 SPM** 是对应 2.4 m/s 的合理值。如果你把速度调快了，步频也建议跟着上调（经验值 175~185），免得步幅变得不现实。

### 半径（m）

只有「跑道圈」用得到。范围 5 ~ 200。

填 **39** 时绕一圈约 **398 米**，和标准 400 米跑道接近。操场小一点就相应减小（半径 30 → 约 306 米，半径 36.5 对应标准跑道的弯道半径）。别填太小的值（比如 5 米），那会绕得极密，轨迹看着像原地转圈。

## 第 8 步 · 验证模块真的生效了

**不要跳过这一步。** 等到跑完才发现没生效，浪费的是你的时间。

### 8.1 看日志

模块每装一个 hook 都会打日志，tag 是 `RunSpoof` 和 `LSPosedFramework`。

```bash
adb logcat -c    # 先清空
# 打开目标 App
adb shell am start -n com.zjwh.android_wh_physicalfitness/.mvi.splash.SplashActivity
sleep 10
adb logcat -d | grep -E "RunSpoof|config read back|route="
```

**正常的输出长这样**（模块会注入到目标 App 的**多个进程**，所以不同进程的日志是交错出现的，顺序每次都不一样）：

```
I RunSpoof: module loaded, process=com.zjwh.android_wh_physicalfitness, systemServer=false
I RunSpoof: target package loaded: com.zjwh.android_wh_physicalfitness, remotePrefs=true
I RunSpoof: config read back: center=<你保存的中心点> speed=4.2 cadence=172.0 radius=39.0 pathPts=19 sig=file:1792368869000:926
I RunSpoof: cfg[0] file channel OK, pathPts=19
I RunSpoof: route built: pts=19, center(wgs)=<转换后的中心点>, converted=true
I RunSpoof: requestLocationUpdates hooked
I RunSpoof: registerGnssStatusCallback hooked
I RunSpoof: sensor register/unregister hooked
I RunSpoof: WifiManager hooked
I RunSpoof: TelephonyManager hooked
I RunSpoof: Location getters overridden (time-based)
I RunSpoof: anti-cheat scrubbed
I RunSpoof: dispatchers started
I LSPosedFramework: system hooks installed, route=377m, center=<转换后的中心点>
```

（`LSPosedFramework` 是 LSPosed 框架给模块日志加的前缀，所以同一条 `log()` 有时显示成 `I RunSpoof:`、有时显示成 `I LSPosedFramework:`，两条都是模块打的。）

**关键看三行**：

- `cfg[0] file channel OK, pathPts=19` —— 配置文件读到了，19 个点
- `route built: pts=19, center(wgs)=..., converted=true` —— **坐标系转换执行了**。`center(wgs)` 应该比 `config read back` 里的中心点**偏离约 370 米**（GCJ-02 → WGS-84 的固定偏移，随地区变化但量级如此）。如果这两个数完全相等、或 `converted=false`，说明转换没生效。
- `route=377m, center=<转换后的中心点>` —— 路线建好了（`route=` 后面是这条路径的实算周长，跟你画的形状有关），并且中心点已经是**你保存的那一个**而不是默认值

如果 `pathPts=0`，说明配置文件是空的或者没建 —— 回[第 5 步](#第-5-步--建配置文件-最容易漏的一步)。

如果整段日志里压根没有 `RunSpoof` 字样，说明模块根本没注入 —— 回[第 3 步](#第-3-步--让-lsposed-认识这个模块)查作用域和 META-INF 位置。

### 8.2 验证坐标真的变了

**别用 `dumpsys location` 和 `NetworkLocationProvider` 的日志判断**——这两处显示的是系统 provider 的 `last location`，可能是模拟器自带 GPS 的历史缓存，跟模块注入到 App 进程里的坐标不是一回事。实测过：那里显示的还是旧坐标，但 App 里跑的位置已经是对的。

真正可靠的验证是**看目标 App 自己的地图**：

1. 打开运动世界校园
2. 进「运动」→ 地图上会显示当前位置
3. 点开始，地图放大到操场级别，应该能看见你的位置落在**你画的操场轮廓上**
4. 轨迹线（绿色，正在增加的部分是红色）沿着你画的形状走

实测截图里，示例操场的 19 点环被 App 完整接受并画了出来，形状与地图上运动场画的跑道轮廓对齐，且地图上**没有**「不在有效区域内」的红字，1–5 号打卡点全部落在跑道上。

> 一个容易误判的现象：`adb shell dumpsys location` 里 `gps provider` 的 `last location` 可能一直停在某个固定坐标，而且 `E GnssUtilsJni: IGnss injectLocation() failed.` 那条报错也照旧。**两者都不影响模块工作**——模块走的是 App 进程内的 `Location` getter 接管与 listener 派发，不依赖系统 provider 的状态。

### 8.3 在编辑器里反向确认

回到「RunSpoof 路线」，如果顶部显示「路径 19 点 ｜ 绕一圈 384 米」，并且地图上画着你的路线，说明模块写盘是通的。

在这里改个参数点保存，然后回到 8.1 看日志，应该出现：

```
I RunSpoof: config reloaded: file:1792368954000:816
```

这是热重载——**改完配置不用重启 App，3 秒内自动生效**。

### ★ 8.3b 如果轨迹整体偏出去约 370 米

这是坐标系问题，不是配置没读到。判据：`config read back` 里的中心点和你保存的一致，但 App 地图上的轨迹整条偏到跑道外面、红字「不在有效区域内」。

原因是编辑器底图是高德瓦片（GCJ-02），而 `Location` 要 WGS-84。本仓库的 `Geo` 类会自动转换，**aapt2 打包后跑 `route built: ... converted=true` 就说明转了**。如果换成你自己改过的版本，检查两处：

1. `RouteEngine.applyConfig()` 里 `Geo.pathGcjToWgs(cfg.path...)` 有没有被执行；
2. `RunSpoofModule` 里高德那一侧的 `getLatitude`/`getLongitude`/`fillAmapLocation` 有没有**转回去**（`Geo.wgsToGcj`）。只改一半会变成「判区对了、地图上还偏」。

详见 [docs/00 的 B0](00-踩坑总览.md#-b0-两个坐标系被当成一个位置整体偏移约-370-米)。

### 8.4 三条自检的优先级

按可靠性从高到低：

| 检查 | 可靠性 | 说明 |
|---|---|---|
| App 地图上的位置/轨迹形状 | ★★★ | 用户真正看到的，也是唯一算数的 |
| `cfg[0] file channel OK, pathPts=N` | ★★★ | 配置读到了没 |
| `system hooks installed, center=...` | ★★★ | `center=` 是不是你画的那个点 |
| `dumpsys location` / `NetworkLocationProvider` | ★ | 可能是系统 provider 的历史缓存，别拿它下结论 |

## 第 9 步 · 在校园跑里正常跑

### 跑之前先确认三件事

1. **时间在有效窗口内** —— 各校时间窗不同，**以你 App 规则页写的为准**；窗口外开跑整条记录都不计入
2. **路线在有效区域内** —— 只有学校指定的场地有效。跑完显示「不在有效区域」，90% 是坐标偏了
3. **配速在你校的区间内** —— 见[第 7 步](#第-7-步--调速度与步频)

### 卡在「跑区有效时间已更新，请重新选择」怎么办

点 GO 时如果弹这个 Toast，是 App 认为你选的跑区时间段过期了（换天、换时段、或服务端下发了新的跑区配置）。处理：

1. 点「晨跑」那个按钮（在「学校要求」右边），弹出「选择跑区」面板
2. 重新点一次 **晨跑**
3. 再点 GO

有时候会连着弹两次，重新选两次就好。如果面板里「课外跑」是灰的，说明当前时段只开放晨跑，正常。

> 另一个坑：**设备时间不对也会卡在这里**。如果模拟器/手机时间是错的（比如比真实时间慢两小时），App 会按那个时间去比对窗口，永远匹配不上。先把设备时间校准到北京时间再试：
> ```
> adb shell "settings put global auto_time 0"
> adb shell "date MMDDhhmmYYYY.ss"     # 例：101909012026.00 = 10月19日 09:01 2026年
> adb shell date                        # 确认
> ```
> 更快的方法是打开「自动设置时间」联网同步。

### 操作流程

1. 打开运动世界校园
2. 进「运动」→ 选 **计分跑**（不是户外跑）
3. 点开始
4. **把手机放桌上就行**，模块自己在推数据（不用真的走）
5. 跑够你校要求的里程（最低里程限制见你 App 规则页），点结束

结束方式是**长按红色圆按钮 3 秒**（`input swipe x y x y 3000`），短按不会结束。跑的过程中底部黑色面板可以往上拖，露出「继续 / 长按结束」两个按钮。

### 计分跑 vs 户外跑

这两个模式判定不一样：

| 模式 | 判定 | 说明 |
|---|---|---|
| **户外跑** | 只算里程，不计成绩 | 可以用来先验证模块是否生效 |
| **计分跑** | 要跑过**必经点 + 若干普通点**才计分 | 真正影响体育成绩的入口（点位数由各校设定） |

**建议第一次先用户外跑验证**：能拿到里程、显示「达标」，说明位置和步态全通了。计分跑还额外要求穿过打卡点，如果路线没经过打卡点，会显示 0 公里 / 不达标——那不是模块坏了，是路线位置不对。

### 关于打卡点

计分跑要求跑过**若干指定点位**（数量与位置由各校后台设定，在你 App 的地图页能看到）。这些点在 App 地图上有编号标记。

所以画路线时最好**画在打卡点附近**，让轨迹能覆盖到它们。如果画在操场另一侧，可能一圈都碰不到打卡点。

**实测到的完整打卡流程**（示例操场，5 个点）：

| 阶段 | 顶部提示 | 进度 |
|---|---|---|
| 刚进跑步页 | 点位1 / 下一点位 | 1/5 |
| 跑过第 1 个点 | 点位5 / 已打卡 | 2/5 |
| 继续 | 点位3 / 已打卡 | 3/5 |
| 继续 | 点位2 / 已打卡 | 4/5 |
| 全部经过 | **已打卡全部点位** | 5/5 |

打卡点会在地图上显示成带编号的绿色圆标（1、2、3、4、5），经过一个就变成绿色对勾。跑的时候地图会放大到操场级别，轨迹用绿线画出来、还在增加中的部分是红色。

**但是**：5/5 全打卡 ≠ 成绩一定有效。跑完还有一道设备时间校验，见下一节。

## 附 · 参数速查表

### 换算公式

```
配速(分/公里) = 1000 ÷ 速度(m/s) ÷ 60
步幅(米)      = 速度(m/s) ÷ 步频(SPM) × 60
绕圈长度(米)  ≈ 4 × 半径 + 2 × π × 半径 = 10.28 × 半径   （跑道圈是两条直道 + 两个半圆，
                                 直线段长 2×半径，所以不是圆周长 2πr）
```

### 各参数合法区间

| 参数 | 界面可调 | App 有效区间 | 默认 | 建议 |
|---|---|---|---|---|
| 速度 | 1.9 ~ 5.4 m/s | 配速落在你校区间 | 2.4 | 2.4 ~ 3.0 |
| 步频 | 45 ~ 290 SPM | 落在你校区间 | 172 | 172 ~ 185 |
| 半径 | 5 ~ 200 m | — | 39 | 39（≈398 米一圈） |
| 中心纬度 | — | 须在有效区域 | 0.0（未设） | 你学校的操场 |
| 中心经度 | — | 须在有效区域 | 0.0（未设） | 你学校的操场 |

### 配置文件格式

`/data/local/tmp/runspoof_route.txt`，纯文本，两种路径写法都支持：

```ini
centerLat=<你的中心纬度>
centerLng=<你的中心经度>
radiusM=39.0
speedMps=4.2
cadenceSpm=172.0
path=<lat>,<lng>;<lat>,<lng>;<lat>,<lng>
```

或者逐行：

```ini
point=<lat>,<lng>
point=<lat>,<lng>
```

路径点格式是 `纬度,经度`，多个点用 `;` 分隔。

**可以直接手改这个文件**，改完 3 秒内自动生效，连 App 都不用重开。这在批量调参时比点界面快得多。

## 附 · 从源码构建

### 依赖

| 需要 | 版本 | 说明 |
|---|---|---|
| JDK | **17** | javac 用 `--release 11` |
| Android SDK | build-tools **34.0.0** + platforms **android-34** | 只有这两个版本被验证过 |
| libxposed API | **102** 的 `classes.jar` | 从 LSPosed 发布包里提取 |

仓库**不含** Gradle。原因很实际：这套东西是在一台没有 Android Studio 的机器上手搓出来的，后来发现无 Gradle 反而更好——整条链就六步，每步失败原因都看得见。

### 一条命令

```powershell
cd <仓库目录>

.\build.ps1 `
    -Sdk   'D:\toolchain\android-sdk' `
    -Jdk   'D:\toolchain\jdk17' `
    -ApiJar 'D:\tools\libxposed-api102\classes.jar' `
    -VersionCode 25 `
    -VersionName '3.2'
```

产物在 `dist\RunSpoof-v41.apk`。

### 它做了什么

```
[1/6] javac      → 编译 6 个 .java 成 17 个 .class
[2/6] d8         → 转成 classes.dex
[3/6] aapt2 link → 生成 base APK（manifest + resources）
[4/6] jar uf     → ★ 把 classes.dex 和 META-INF/xposed/ 塞进根目录
[5/6] zipalign   → 4 字节对齐
[6/6] apksigner  → 签名
```

第 4 步是最关键的。`aapt2 -A assets` 在 Windows 上会把路径写成反斜杠，LSPosed 完全不识别，所以改用 `jar uf` 以正斜杠相对路径加入。

脚本最后会**自校验**，打印 APK 条目并检查 `META-INF/xposed` 是否在根目录、是否正斜杠命名。看到：

```
==> 校验通过：META-INF/xposed 在 APK 根目录，正斜杠命名。
```

才算成功。

### 签名

默认用 `build\debug-keystore.p12`（首次构建自动生成，密码 `runspoof`）。想用自己的：

```powershell
.\build.ps1 ... -Keystore 'D:\my\release.p12' -KsAlias runspoof -KsPass '你的密码'
```

> **别把密钥提交进仓库。** `.gitignore` 已经把 `*.jks` / `*.p12` / `*.keystore` 全排除了。

### 只出未签名包

```powershell
.\build.ps1 ... -NoSign
```

### ★ 必须校准设备时间

这是踩过的坑里**唯一一个会让成绩白跑的**，而且提示文案不会直接说「时间不对」：

```
为了您跑步记录的有效性，请修改为准确的北京时间后再上传记录
```

模拟器/刷机设备的默认时钟常和真实时间差几个小时。App 拿设备时间去跟服务端下发的跑区时间段比对，对不上就拒绝上传——你已经跑完一整场、打卡全过，成绩照样作废。

**跑之前**先校准：

```bash
adb shell "settings put global auto_time 0"
adb shell "date MMMDDhhmmYYYY.ss"   # 月日时分年.秒，例：101909012026.21 = 10/19 09:01
adb shell date                      # 回读确认
```

真实手机上打开系统「自动设置时间」即可。跑前花十秒看一眼设备时间，比跑完四十分钟发现传不上去划算。

### 关于「配速过快」标红

速度 4.2 m/s（配速 3'58"）时，起步阶段前三圈配速会瞬时掉到 2'43"、2'56"，界面标红「配速过快」。这是小样本下 `距离/时间` 比值抖动造成的，跑开一段就收敛。速度建议 **2.4 ~ 3.0 m/s**，离区间边界留余量。
