# 第三轮改进：恒定值与跨通道一致性

> 范围：本仓库为**公开仓库**，本文不含任何真实场次的实测数值、坐标、账号信息。
> 所有结论均可由 App 自身记录（`laps_json` / `segment_json` / `speed_json` /
> `step_freq_json`）定性复现，复算脚本见 `_tools/harness` 与本仓库 `docs/00`。

## 问题的来源

第一、二轮修的是「时间轴污染」与「采样量化」——都是**位置侧**的问题。
把 App 自己的记录横向拉齐之后，还剩下两类**与位置无关**的破绽：

| 类别 | 表现 | 为什么危险 |
|---|---|---|
| **恒定值** | 某个字段在整个场次里一个值都不变 | 不依赖任何外部参照，单字段就能判 |
| **跨通道不一致** | App 同时采集的两个数据源，推算出互相矛盾的结论 | 交叉一算即得，且无法用「噪声」解释 |

这两类比「数值偏了一点」严重得多：偏了一点还能用 GPS 误差、人体波动解释，
**而恒定和不一致没有物理解释**。

---

## 一、海拔：从常量变成时间的函数

### 旧行为

`Location.getAltitude()` 直接 `return 100.0d`，AMap 那条路同样是 `mAltitude = 100.0f`。

### 后果（可从 App 记录定性看出）

App 的 `laps_json` 里 `endAltAbs` / `elevationGain` / `endAltRel` 三项都取自海拔：

- 模块在场时：这三项**每一圈完全相同**，且 `elevationGain` **恒为 0**；
- 模块接管之前（App 拿真实 GNSS）：这三项**随圈次变化**，量级与当地地形相符。

### 两层破绽，第二层更严重

1. **逐圈恒定**：真人跑一段路，不可能每公里爬升恰好 0 m。
2. **绝对量级**：写死 100.0 会让上报海拔与所在地地形对不上；
   很多城市的海拔与这个值差上千米。

还有第三层，是这次才想清楚的：**写死常量意味着所有使用者上报同一个海拔**。
这不是单账号的特征，而是**可跨账号聚合的全局指纹**——一个
`COUNT(DISTINCT endAltAbs) = 1` 的聚合查询就能把使用者圈出来。

### 改法

`GaitEngine` 增加：

```java
double altitude(double elapsedSec)          // 基准 + 极缓坡度 + 平滑起伏
double altitudeRelative(double elapsedSec)  // 对应 endAltRel
```

三者都是解析可算的（基准常量 + 正弦坡 + 平滑噪声），所以：

- 跨进程一致（主进程与 pushservice 算出同一个值，不会自相矛盾）；
- 不需要逐帧累加状态；
- 每公里能拿到非 0 的爬升。

基准值改为配置项 `ConfigStore.Config.altBaseM`（NaN = 没设过）。四条通道全部打通：
`/data/local/tmp` 文件、SharedPreferences、XML、以及 UI 输入框。
**用户必须按自己所在地填**，留空则退回兜底值并给出提示——
因为「所有人用同一个基准」正是要消灭的那个指纹。

### 验证

无头仿真台（真实 `GaitEngine`）：

- 海拔 span 非 0，每公里爬升非 0 且量级合理；
- 设备端 `VITALS alt=<min>/<max> span=<span> ... -> VARIES`（具体数值不记录）。

## 二、定位精度：同样是常量

旧版 `getAccuracy()` 直接 `return 4.0f`，`setVerticalAccuracyMeters(0.8f)` 也是常量。

真机在开阔操场上，水平精度随卫星几何、多径、遮挡在数米内漂；
恒定精度同样属于上述「恒定值」破绽，而且 App 会拿它参与
速度/里程的不确定度评估。

改法：`horizontalAccuracy()` = 基准 + 平滑起伏；`verticalAccuracy()` ≈ 水平 × 1.7。

## 三、步频双通道不一致（本轮最值得修的一条）

### 旧行为

App 同时订阅两个计步传感器：

- `STEP_COUNTER`（type 19）：累计步数，模块按 `floor(steps())` 播；
- `STEP_DETECTOR`（type 18）：每步一个事件，模块按
  `Math.max(1, Math.round(cadence / 60))` **每秒一次性推 N 个**。

### 两个问题叠在一起

**(a) 数量对不上。** counter 侧是「累计步数的取整」（积分值），
detector 侧是「瞬时步率的圆整 × 秒数」。两者一个是积分、一个是瞬时速率，
长期必然漂移。仿真台复现出了大面积窗口两通道步频不一致的情况
（`ChannelCheck` 可离线复算）。

**(b) 时间戳全同。** 同一 tick 里推的 N 个事件共用
`SystemClock.elapsedRealtimeNanos()`，于是逐步间隔退化成
`0 / 0 / … / 1000 ms` 的锯齿。真人步间隔是几百毫秒的连续值，
这个锯齿本身就是「这是程序推的」的直接证据。

### 改法：`stepRate()` —— steps() 的解析导数

关键认识：**不能靠「让 cadence 和 steps 各自对」来解决**，必须让两者同源。

```java
double stepRate(double elapsedSec)   // = d(steps)/dt，解析求导而非数值差分
```

推导：`steps(t) = base · B(t) · F(t)`，其中

- `B(t)` 是各项积分的和（含速度耦合、步频波动、步时抖动），
- `F(t)` 是疲劳因子。

于是

```
steps'(t) = base · [B'(t)·F(t) + B(t)·F'(t)]
```

`B'(t)` 直接把各 `integral()` 换成 `value()` 即可；`F'(t)` 是
`−depth · sech²(x) / (60·span)`。这样 `steps()` 的积分形式**完全不用改**
（它的疲劳衰减幅度此前已被现场数据验证过），一致性由 `stepRate()` 显式补偿。

派发侧相应改成：

- 每个事件用**各自的真实跨越时刻**做时间戳（新增 `pushSensorAt()`）；
- 事件数量取 `floor(steps(t))` 的增量，与 counter 侧同源；
- 热重载导致时间轴重置时，重新对齐基线而不是补发。

### 验证

`ChannelCheck`（离线可复算，`_tools/harness`）：

| 指标 | 旧行为（`cadence` 模式） | 新行为（`rate` 模式） |
|---|---|---|
| 10 秒窗口两通道步频差 | 绝大多数窗口不一致（最大差达数十 spm） | **全部窗口 0 差异** |
| 逐步事件间隔 | 0 / 0 / … / 1000 ms 锯齿 | 按真实跨越时刻分摊 |

`GaitCheck` 的导数一致性：`d(steps)/dt` 与 `stepRate()` 的
最大相对误差在 1e-05 量级（数值差分 vs 解析求导，50 ms 中心差分），
即数值噪声水平，可视为恒等。

> ⚠️ **一处容易混淆的地方**：`GaitCheck` 的 B 项比的是 `stepRate()` 与
> `cadence()` 两个**公式**，会报出百分级差异。这不是缺陷——
> `cadence()` 是「瞬时步频」，`stepRate()` 是 `steps()` 的解析导数，
> 两者在疲劳段本就不同源（`steps()` 的疲劳是乘在整条积分曲线外侧，
> 见 `steps()` 注释）。真正决定 App 观感的是**实际派发出去的两个通道**，
> 它们同源于 `stepsFloat()`，由 `ChannelCheck` 验证为 0 差异。
>
> 教训与 §四 那条同型：**自检要量「实际发出去的东西」，不能量「另一套公式」**，
> 否则报出来的是指标错，会把人引到错误的地方去改。

## 四、新增自检：VITALS

把「曾经被写死成常量」的三个量按分钟打出来：

```
VITALS alt=<min>/<max> span=<span> rel=<+x.xx> acc=<min>/<max> emitSteps=<n> emitSpm=<r> -> VARIES
```

判读：`ALT` / `ACC` 的 `span` 必须 > 0；出现 `span=0.000 ... CONSTANT!` 即为回归。
（本文不记录任何一次运行的具体数值。）

> 踩坑记录一：这个自检的**第一版写错了**——它把采样放在分钟边界上，
> 于是 min 和 max 取到同一个样本，`span` 恒为 0，自检永远报 `CONSTANT!`。
> 那是指标错，不是功能错。现在改成每个派发 tick 都调一次
> `accumulateVitals()`，分钟边界只负责汇总与清零。
>
> 踩坑记录二（本次修正）：第二版又把 `currentStepRate()` 与 `currentCadence()`
> 并排打出来做比较，看着像"两通道步频不一致"。但那两个是**两套公式**，
> 不是两条实际通道——真正派发的两个计步通道都源于 `stepsFloat()`，
> 已由 `ChannelCheck` 验证为 0 差异。现在改为打 `emitSteps` / `emitSpm`，
> 直接量**这一分钟实际发出去的步数与增量步频**，与派发同源。
>
> 两次踩的是同一个坑：**自检要量实现真正发出去的东西**。
> 量别的东西，报出来的差异就是指标错，还会把人引去改错的地方。

## 五、一个必须澄清的方法论陷阱：子集和不可用于归因

排查过程中一度想用「服务端字段 vs 本地记录合计」的差额来做归因
（例如「服务端只计入了本地跑量的 X%，说明某些场次被判无效」）。

这条路**在统计上不成立**，值得写下来避免重犯：

- 把 18 场里程当候选集，2^18 = 262144 个子集；
- 对一个给定目标值，落在给定容差内的子集数**与随机目标同量级**
  （同一规模下二者只差数倍，不具备判别力）；
- 也就是说，**任何**数值都能被「凑」出来，命中不具有统计意义。

所以差额只能说明「服务端与本地口径不同」，**不能**说明「哪几场被扣」
或者「扣了多少比例」。要归因必须拿到服务端的判定理由码
（`antCheating/details` 一类），而不是从合计值反推。

同类错误此前也犯过两次，都是**单位错觉**：

- `segment_json.avgSpeed` 实为**配速 min/km**，不是速度；
- `segment_json.avgStep` 实为**步频 spm**，不是步数
  （把它当步数除以时长会虚高约 3 倍）。

规律：**拿到一个字段先验证语义，再参与计算**。验证方法很简单 ——
用两个独立通道去推同一个物理量，对不上就说明至少一个字段被读错了。

## 八、仍然没解决的部分（诚实记录）

1. **服务端判定违规的具体理由码拿不到。** App 侧有
   `api/v670/runnings/hardware/antCheating/details` 与 `AntCheatingDetailsEntity`，
   但只在跑步详情页触发；账号处于冻结期，无法产生新场次去触发它。
   这是后续最有价值的突破口。
2. **本轮的收益尚未在真实计分跑里复测。** 与前两轮相同，改动在仿真台与
   模拟器上都验证了机制生效，但「服务端是否因此不再判违规」需要等冻结解除后
   跑一场才能回答。**不能把「自检通过」当成「不会被判违规」。**
3. **海拔基准靠用户填。** 留空时仍是兜底常量，只是从「所有人都一样」
   变成「没填的人一样」。要彻底消除需要从真实定位里取一次高程序列。
