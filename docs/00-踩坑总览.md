# 00 · 踩坑总览

按「症状 → 根因 → 结论」索引。带 ★ 的是真正让人卡了很久、且换环境极易复发的。

## A. 模块框架层

### ★ A1. LSPosed 2.2.1 不认 legacy Xposed API 82

**症状**：模块装了、作用域勾了、重启了，LSPosed 模块列表里始终「未激活」；logcat 里模块类从未被加载。

**根因**：LSPosed 2.2.1 起弃用 `de.robv.android.xposed:api:82` 那套 legacy 入口，只认 **libxposed 新格式**（`META-INF/xposed/`，API 101+）。

**结论**：模块必须声明

```
META-INF/xposed/module.prop     → minApiVersion=101 / targetApiVersion=102
META-INF/xposed/scope.list      → 默认作用域包名
META-INF/xposed/java_init.list  → 模块入口类全名
```

并且入口类继承 `io.github.libxposed.api.XposedModule`，实现 `onPackageLoaded(...)`。

---

### ★★ A2. `META-INF/xposed/` 必须**在 APK 根目录**，且路径用**正斜杠**

这一条是最隐蔽的，因为它**完全不报错**——模块就是安静地不生效。

**症状**：APK 装上了，LSPosed 里能看到模块，但从不加载；用 `unzip -l` 看 APK 才发现条目长这样：

```
assets/META-INF/xposed/module.prop     ← 错：被塞进 assets
META-INF\xposed\module.prop            ← 错：反斜杠
```

**根因**：

1. `aapt2 link -A assets` 会把 `assets/` 下的内容**整体平移到 APK 的 `assets/` 目录**，于是 `assets/META-INF/xposed/` 变成 `assets/META-INF/xposed/`。LSPosed 只查根目录。
2. 即使想办法绕开第一点，**aapt2 在 Windows 上把资源路径写成反斜杠**，条目名变成 `META-INF\xposed\module.prop`。ZIP 规范要求正斜杠，LSPosed 按 `/` 查找，于是查不到。

**结论**：`META-INF/xposed/` 三个文件**必须用 `jar uf` 逐个添加**，不要走 `aapt2 -A`：

```powershell
Push-Location $Stage          # $Stage 下是 META-INF/xposed/*.prop 等
& $Jar uf $Apk 'META-INF\xposed\module.prop' 'META-INF\xposed\scope.list' 'META-INF\xposed\java_init.list'
Pop-Location
```

`jar.exe` 写入的条目名是标准正斜杠。

**构建脚本里已内置自校验**（`build.ps1` 最后检查 APK 条目），不要删掉那段。

---

### A3. `ConfigStore.attach()` 从来没被调用

**症状**：地图界面保存成功（Toast 也弹了），但模拟行为不变，仍是内置默认值。

**根因**：注入侧读配置靠 `XposedModule.getRemotePreferences("runspoof")`，但 **`attach()` 没被调用过**，`remote` 一直是 `null`，于是每次读配置都回落到默认值。

**结论**：`onPackageLoaded()` 的**第一件事**就是 `ConfigStore.attach(this)`，早于任何 `RouteEngine` 初始化。

## B. 定位层

### ★★★ B0. 两个坐标系被当成一个：位置整体偏移约 370 米

**症状**：配置读对了（日志 `pathPts=19`、`center=...` 都是用户画的那份），但 App 地图上的轨迹整体偏到跑道外面、红字「不在有效区域内」；把坐标系换过之后同一个配置立刻就对了。

**根因**：三个环节用的不是同一个坐标系，而代码里一次转换都没有。

| 环节 | 实际坐标系 |
|---|---|
| 路线编辑器底图 | **GCJ-02**（高德瓦片，全部数据都是火星坐标） |
| `android.location.Location` | **WGS-84**（Android 的约定） |
| App 判区 / 服务端校验 | **WGS-84** |

用户在编辑器的瓦片上点出来的经纬度是 GCJ-02，旧版本把它原样塞进 `Location` 推给系统。于是 App 拿到一个「自称 WGS-84 其实是 GCJ-02」的坐标，画到高德地图上时又做一次 WGS→GCJ 偏移，**同一个错误被叠加了两次**，看起来像两个独立的 bug。

实测（坐标已脱敏，只保留偏移量级）：同一位置从 GCJ-02 换到 WGS-84，**水平偏移在数百米量级**（该量级随地区变化，国内大部分地区都是这个范围）。这个偏移量**随地区变化，不能写死**，必须现算。

**结论**：新增 `Geo` 类做双向换算，并明确约定两边各要什么：

- 配置文件里**永远存 GCJ-02**（因为来源和显示都是高德瓦片，用户看到什么就存什么）；
- `RouteEngine.applyConfig()` 里统一转成 **WGS-84** 再建路线，之后位置/速度/bearing 全在 WGS-84 下算；
- 高德那一侧的 hook（`AMapLocation.getLatitude()`、`fillAmapLocation()` 里的 `mLatitude`）**反过来转回 GCJ-02**，因为 `AMapLocation` 的约定是火星坐标。

三条路都从 `RouteEngine` 的同一个 WGS-84 位置出发，各自按需转换。漏掉任何一条，那一侧就会单独偏 370 米。

**验证方法**（比看地图更直接）：日志里现在会同时打印原始与转换后的中心点：

```
config read back: center=<配置里的中心点>,... pathPts=19
route built: pts=19, center(wgs)=<转换后的中心点>, converted=true
system hooks installed, route=377m, center=<转换后的中心点>
```

`config read back` 是配置里的原值（GCJ-02），`center(wgs)` 是实际推给系统的值，`converted=true` 表示转换确实执行了。如果两者相等，说明转换没生效。

### ★B1. 高德 SDK 的「用到」和「用于定位」是两回事

**症状**：`hookAMap` 一直打印 `AMapLocation not present, skip AMap hooks`，但 APK 里明明有高德。

**根因（分两层）**：

1. **时机**：`onPackageLoaded` 阶段 App 自己的类还没加载完，`Class.forName("com.amap.api.location.AMapLocation")` 必然抛 `ClassNotFoundException`，整段 hook 被静默跳过。要在 `onPackageReady` 里再试一次。
2. **更关键的事实**：这个 App **用高德画地图，但不用高德定位**。
   - `com/amap/api/maps` 在 dex 里出现 331 次（地图渲染，Polygon / PolygonOptions / LatLng）
   - `com/amap/api/location` 只出现 36 次，且 `AMapLocation` 类**不在 base.apk 里**（`javap` 直接找不到），属于动态加载/可选路径
   - 决定性证据：`dumpsys location` 里能看到 App 用**系统 gps provider** 注册了请求
     （`gps provider +registration 10052/com.zjwh...`）

**结论**：定位链路是**系统 `LocationManager`**，所以 hook 系统层方向是对的，`AMapLocation not present` 只是一条无害日志，不是失败信号。不要因为它去改定位方案。

> 教训：判断「App 走哪条定位链路」要看 `dumpsys location` 的 registration 记录，不要因为 dex 里出现某个 SDK 的字符串就下结论。字符串出现次数 ≠ 实际调用路径。

### ★★ B1b. 「不在有效区域内」的判定是**多边形包含**，且有服务端下发的区域

**结论**：dex 里有 `isValidPoint`、`Polygon`/`PolygonOptions`、`LatLng`，配置字段是 `runAreaId` / `areaList` / `pointList`，提示语「不在有效区域内」是服务端文案。也就是说：**坐标必须落进服务端下发的多边形内**，光在「图上看着差不多」不行。

跑的时候还要满足点位打卡（界面上是「已打卡 0/5」这种形式），所以轨迹必须**反复经过**那些点位，而不是从一个区域穿出去。

这也是为什么 `RouteEngine` 默认生成的是**闭合环**而不是直线 —— 直线跑一次就出界，环线才能持续留在区域内并扫过点位。

### ★★ B2. `requestLocationUpdates` hook 里 `return null` 会让 App 永远收不到位置

**症状**：hook 挂上了，日志也有，但 App 一次定位回调都没收到。

**根因**：旧实现里 hook `LocationManager.requestLocationUpdates(...)` 直接 `return null`（想「吞掉」注册，改由模块主动推位置）。**但系统层因此根本没有监听器**，模块后来推的 `Location` 对象没有接收方，App 自然收不到任何回调。

**结论**：**必须 `chain.proceed()` 让注册真实发生**，位置改由 dispatcher 主动推送（同时 hook `onLocationChanged` 入参替换）。

---

### ★B3. GNSS 回调不能改 `chain.args[i]`——Android 15 上是 `ImmutableList`

**症状**：hook `onSvStatusChanged` 后 App 报「GPS 信号弱」，真实卫星回调被整条吞掉。

**根因**：Android 15 的 `GnssStatusTransport.onSvStatusChanged` 参数是 `ImmutableList`，`chain.args[0] = spoofedStatus` 抛 `UnsupportedOperationException`；异常发生在 `proceed` 之前，于是**真实回调也没了**。

**结论**：用 `GnssStatus.Builder` 造**新对象**，然后 `chain.proceed(new Object[]{ newStatus, ... })` 单独传参，绝不去 mutate `args`。

---

### ★B4. 全局 hook `Location.getLatitude()` 会让 `distanceTo()` 恒为 0

**症状**：位置看起来对，但里程一直 0 米。

**根因**：`getLatitude()` 被全局 hook 成「返回当前时刻的坐标」。任何两个 `Location` 对象调用 `distanceTo()` 时，**两边都取到同一个当前坐标** → 距离恒 0.0。App 用 `distanceTo` 逐点累加里程，于是永远 0 米。

**结论**：`getLatitude()/getLongitude()` 必须按**每个 Location 自己的时间戳**去算坐标：

```java
long t = timeOf(location);            // 用对象自己的时间，不是「现在」
double[] p = RouteEngine.positionAt(t);
```

这样不同时刻的 `Location` 自然对应不同位置，`distanceTo` 恢复正确。

> ⚠️ 本条早期写的是「用 `location.getTime()`」，**那句话直接造成了 B6 的成绩作废**。
> 方向没错（要按对象自己的时间），但**取时间的来源选错了**。正确取值见 B6。

### ★★★ B6. `Location.getTime()` 被模拟器污染：分段时长来回跳，成绩作废

**症状**：五个打卡点全部 `isPass:true`、顺序正确、里程配速步频全部达标，
结果页却只报一条「**分段不达标**」。同时地图上的轨迹很难看——
红线穿过操场中部，看着像路线画错了。

**先别怀疑路线。** 打卡点既然全过，轨迹确实经过了那五个点。
穿过中部的直线是**位置瞬移**：这一秒人还在跑道北端，下一秒被甩到南端，
中间用一条直线连起来。所以「路线不对」和「分段不达标」是同一个根因的两个表现。

**根因**：轨迹是「时间的纯函数」`position = f(t)`，而旧版把 `t` 取自
`location.getTime()`。模拟器假 GPS 守护进程 `nemu` 每秒往系统层塞它自己的
`Location`，那份 `Location` 的 `getTime()` 是它自己算的墙钟，
而 `elapsedRealtimeNanos` 是系统按 fix 真实投递时刻赋值的。
每收到一个外来点，位置就被甩到另一个时刻的路线位置上。

**决定性证据**（App 自己写进 `run_data_database.segment_json`，20 秒一档）：

分段边界不是单调递增的，而是在**两条相差数百秒的时间线**之间来回跳：
相邻分段有时前进几十秒、有时又倒退回另一个时刻，跳变幅度远大于一档的
20 秒。这才是问题所在——只看单个分段的时长是看不出来的。

后果直接落在数据上：

- `avgSpeed` 出现远超人类速度（数十 m/s 量级）的鬼魂分段
- `state: 256` —— App 给这些分段打的异常标记
- 整场判「分段不达标」

**怎么区分「时间戳被污染」和「系统时钟被步进」**（表现很像，修法完全不同）：

看**总时长**对不对。这一场的总时长与起点/终点之差**分秒不差**，只有分段边界在跳。若是系统墙钟被步进，总时长会一起被拽走。
所以污染源在**单个 Location 的时间戳**上，不在系统时钟上。

再补两条现场核查：

```sh
settings get global auto_time     # 0 => 系统根本没在对时
logcat -d | grep ntp_failure      # 实测 NTP 全部超时
# 另测 70 秒内 (wall − uptime) 差值抖动 ±15ms => 设备墙钟本身是稳的
```

**结论**：位置和时间都改成从 `elapsedRealtimeNanos` 派生，
并且**接管 `getTime()` 本身**——App 的分段边界就是拿各个 `Location`
的时间戳算的，坐标接管了、时间没接管，分段照样会跳。

```java
// 取时间：读 elapsedRealtime，不读 getTime()
long rtNs = loc.getElapsedRealtimeNanos();
long t = Clock.wallMsForRt(rtNs / 1_000_000L);

// 并且接管 getTime()，让 App 自己算分段时落在同一条干净时间轴上
hookOne(Location.class, "getTime", new Class<?>[]{},
        chain -> timeOf(chain.getThisObject()));
```

`Clock` 锚定一次真实墙钟后只按 `elapsedRealtime` 递推，因此免疫一切时钟步进；
锚定一次是为了绝对时间仍然正确（App 要拿设备时间比对服务端跑区时段，见 G1）。

**两个实现细节，都是这次踩过的**：

1. **`timeOf()` 里绝不能再调 `getTime()`**。`getTime()` 已被 hook 成调
   `timeOf()`，再调回去就是无限递归 → `StackOverflowError`。
2. **不要给 `Clock` 加「单调高水位」钳制**。直觉上想让时间永不倒退，
   但 App 会**稍后重读历史 `Location`** 来算 `distanceTo()`；钳制会把旧 fix
   拉到现在的位置，两点重合，又踩回 B4 那个「里程恒为 0」。
   映射必须是纯仿射的：同一入参永远同一输出。

**还有一条容易写错、且会让上面那条前功尽弃**：兜底分支也不能用「当前时刻」。

```java
// ✗ 错：垃圾值钳到现在 —— 同一 Location 在不同时刻读到不同时间
if (rtMs <= 0 || rtMs > nowRt) rtMs = nowRt;

// ✓ 对：返回固定值，仍可重入
if (rtMs <= 0 || rtMs > nowRt + 60_000) return anchorWall;
```

实测差异：同一 fix 两次读可能相差**数百秒**。App 重读历史点时坐标会跳，
`distanceTo()` 于是算错——正是会放大分段距离的那类错误。
验证方式很直接：同一入参调用两次、中间推进时钟，结果必须相等。

**真机上的判据**（`timeOf()` 加了次生统计，但统计点必须在**派发处**）：

```
TIMELINE n=<次数> neg=0 big>3s=0 minGap≈<周期> maxGap≈<周期> -> CLEAN
```

`n`=派发次数、`neg`=时间戳倒退次数、`min/max`=相邻间隔。
间隔恒定等于派发周期、上下浮动只有几毫秒，说明喂给 App 的时间轴是干净的。

> ⚠️ 统计点放错会打出假警报。一开始把统计放进 `timeOf()`，
> 得到大量 `SUSPECT`——那是**指标错**：`timeOf()` 每秒被调用
> 极多次（App 反复读 getTime/getLatitude/getSpeed），把这些调用放一起比
> 「相邻是否递增」，比的是**不同对象**之间的顺序，天然会乱。
> 该守的是「我们主动派发的 fix 序列递增」，所以统计点在派发处。

**一次 tick 只能造一条 fix**：位置派发里 `buildLocation()` 曾写在 listener
循环内，同一秒 N 个 listener 各拿一条**时间戳不同**的 fix（本该是同一次定位）。
多路取点（gps/fused）时会把同一瞬间看成多个时刻，分段边界被切乱。已提到循环外。

顺带一条：想用反射读 `Location.mTime` 打诊断日志，实测**恒为 0**
（非 SDK 接口被隐藏 API 策略拦掉），据此打的「drift」日志
全是假警报。下负面结论前先确认探测手段本身可用。

### ★B5. MuMu 的假 GPS 有固定偏移，且重启后失效

**症状**：`MuMuManager tool location` 设了坐标，模拟器里的定位却有几十米偏差；或者模拟器重启后完全没定位。

**根因**：
- MuMu 的 `nemu` 假 GPS 有**固定偏移**：经纬度各偏一个固定小量（量级为万分之几度），反向补偿后误差仍有十米级。
- `nemu` 的 last location 在重启后是 `null`，假 GPS 直接失效。

**结论**：**不要让模块依赖模拟器提供的 GPS**。模块应当能独立产出位置——这正是 `RouteEngine` 存在的理由。

## C. 传感器 / 步态层

### ★★ C1. 步频恒为 0：1 Hz 推加速度还原不出 2.75 Hz 步态

**症状**：位置在动、里程在涨，但**步数 / 步频始终 0**，成绩判定不达标。

**根因**：目标 App 只注册加速度计/陀螺仪/方向传感器，**靠加速度波形的峰值数来数步**。App 的加速度回调采样率是数十 Hz 量级（远高于 1 Hz）。按 1 Hz 推送时，一个步态周期里一个采样点都采不到 → 数不出峰 → 步频 0。

**结论**：按 **50 Hz** 推送，并且波形要是**真实可数峰**的：

- 高斯峰查表波形（不是简单正弦，正弦在低采样率下峰不够尖）
- 零均值（否则 App 的峰检测阈值会漂）
- `hashUnit(seed, stepIndex)` 让每一步的峰高/峰宽有确定性抖动（同样的 seed 每次都一样，便于复现）
- 正弦叠加噪声后**解析积分**，保证速度和位移仍然自洽
- 左右脚交替带侧向分量

后续又补了 5 处真实感改进：步行/跑步 `smoothstep` 混合、左右腿 1~3% 不对称、步时抖动 CV≈1.5%、传感器量化（0.0012 m/s²）+ 60~600 s 慢零偏、12 分钟后 `tanh` 疲劳衰减（最多 -4%）。

---

### C2. 步数不能用「时间 × 固定步频」

**症状**：手动停一下再动，或者改速度，步数和实际位移对不上。

**根因**：固定步频积分出来的步数会和速度积分出来的位移脱钩。

**结论**：**步数 = 速度积分**；**步频 = 速度 × 60 / 步幅**，其中 `步幅 = 0.75 + 0.28 × 速度`。这样改速度时步频自动跟着变，永远自洽。

---

### C3. 传感器 listener 用 listener 做 key 会互相覆盖

**症状**：同一个 listener 注册了加速度计 + 陀螺仪时，只有最后一个传感器有回调。

**根因**：`Map<Object, ...>` 用 listener 实例做 key，第二个 `registerListener` 把第一个覆盖了。

**结论**：用 `(listener, sensorType)` 组合做 key；并且**必须 hook `unregisterListener`**，否则已注销的 listener 还在被推送（App 会收到不该收的回调，甚至崩）。

---

### C4. 50 Hz 派发跑在主线程会卡

**症状**：目标 App 明显卡顿、掉帧。

**根因**：50 Hz × N 个 listener 的回调全压在 app 主线程上。

**结论**：独立 `HandlerThread` 派发。同时缓存 `SensorEvent.mValues` 字段和 `onSensorChanged` 方法引用（否则 50 Hz × N 次反射查找）。

## D. 配置 / 权限层

### ★★D1. 配置从 UI 传到注入进程：三条路，只剩一条

这个问题花了最长时间，因为它**每一层都不报错**。最终结论：只能用 `/data/local/tmp` 文件通道，而且**文件必须由用户先用 adb 建好**。

**症状**：编辑器里画得好好的、配置也保存了，但目标 App 里跑的还是代码默认值（`center=0.0,0.0`）。logcat 里 `config read back` 打出来的永远是默认值。

**通道一：libxposed remote preferences —— 静默返回空表**

```java
XposedPreferences p = getRemotePreferences("runspoof");   // 不抛异常
p.getString("centerLat", "DEFAULT")                        // 拿到 "DEFAULT"
```

LSPosed 2.2.1 + API 102 上调用成功、无异常、无日志，但表是空的。

决定性证据：查 LSPosed 自己的数据库

```bash
sqlite3 /data/adb/lspd/config/modules_config.db \
  "select * from module_configs"
```

`module_configs` 表里**只有上游 LocationSpoofer 的记录**（`com.vincenthzr.locationspoofer|0|locationspoofer_config|snapshot|1248`），我们模块的名字一次都没出现过——说明写入从未经过框架。

**通道二：直读模块的 `shared_prefs/runspoof.xml` —— 那个文件在注入进程里不存在**

注入进目标 App 的代码跑在**目标 App 的 uid**（10052）里。Android 10+ 的 per-app data isolation 让每个 App 的 mount namespace 里 `/data/data` 是一份独立的 tmpfs，**只挂它自己那一份**。

所以 `new File("/data/data/com.qf.runspoof/shared_prefs/runspoof.xml").exists()` 在注入进程里恒为 `false`。

这不是权限问题，试过这些都没用：

| 尝试 | 结果 |
|---|---|
| `chmod 644` prefs 文件 | 无效 |
| `chmod 711` 上两级目录 | 无效 |
| `restorecon -Rv` 修 SELinux 标签 | 无效（且所有 avc denial 都是 `permissive=1`，只记录不拦截） |
| 关掉 SELinux | 无效 |

**根本原因**：文件在那个 namespace 里**压根没被挂载**，跟权限无关。

**通道三：`/data/local/tmp` 文件 —— 能用，但普通 App 建不了文件**

`/data/local/tmp` 的权限是 `drwxrwx--x shell shell`（**0771**）：

- owner `shell` 可写
- group `shell` 可写
- other 只有**进入**权限，**没有写**

普通 App uid 既不是 `shell` 也不是 root → **创建文件失败**（`open()` 返回 EACCES）。

但**写一个已经存在的文件**只需要文件本身可写，不需要目录写权限。所以：

```bash
adb shell "touch /data/local/tmp/runspoof_route.txt; chmod 666 /data/local/tmp/runspoof_route.txt"
```

这条命令**不需要 root**（普通 `adb shell` 就是 shell uid，`/data/local/tmp` 是它自己的目录）。做完之后模块就能一直往里写。

**所以最终方案是**：

1. 用户执行上面那条 `touch` + `chmod`（教程里放在第 5 步，标了「最容易漏的一步」）
2. UI 保存时写这个文件，注入侧每秒/每 3 秒读这个文件
3. 写失败时 UI 弹框，直接把这条命令显示出来

**怎么快速判断自己漏了这步**：logcat 里

```
I LSPosedFramework: system hooks installed, route=..., center=0.0,0.0
```

`center=` 是 `0.0,0.0` 就是没读到（那是「还没设过」的默认值）。

已有文件时日志会打：

```
I RunSpoof: cfg[0] file channel OK, pathPts=19
I LSPosedFramework: config read back: center=<你保存的中心点>,... pathPts=19 sig=file:1792369293208:926
```

**顺带记下的经验**：排查这类问题时，「调用没报错」不等于「调用成功了」。remote preferences 静默返回空表这点，直到加了 `describeRemote()` 把表内容 dump 出来才看清。

### ★D2. 地图从 unpkg.com 加载 Leaflet 在国内会白屏

**症状**：地图界面一片空白，只有按钮。

**根因**：旧版从 `unpkg.com` 拉 Leaflet，国内网络经常拿不到。

**结论**：改成**自带瓦片地图**（纯 HTML/CSS/JS，内嵌在 `MapPickerActivity` 里），只依赖高德瓦片域名，不再需要任何外部 JS 库。

---

### ★D3. 「能点」不等于「能画」——编辑器的三个隐性要求

**症状**：地图界面能点、也能存下坐标，但根本没法用它描一条操场跑道。

**根因**（三条都属于「功能看起来有、实际不可用」）：

1. **只画点不画线**。旧版每个路径点只是一个数字标记，点与点之间没有连线。用户加完几个点，看不出自己画的是一条什么形状的路线，只能凭想象。必须画 `polyline` + 自动闭合的回程虚线。
2. **拖动地图 = 改中心点**。旧版 `render()` 永远把视野锁定在 `cLat/cLng`，而平移逻辑又去改这两个变量。结果是：想看看操场在哪，一拖就把路线中心挪走了，画出来的圈跟着跑。**视野中心和路线中心必须是两套变量**（`vLat/vLng` 与 `cLat/cLng`），拖动只动前者。
3. **编辑即落盘**。旧版点一下地图就直接 `writeUi()`。手一抖就把已保存的配置改掉，没有撤销、没有「取消」。编辑期应该只在内存里，按「保存」才写。

**结论**：一个可用的路径编辑器至少要有 —— 连线可视化、视野与数据分离、编辑/保存两态分离、撤销栈、拖动改点、长按删点。这些都不难，缺任何一个都会让人没法用它完成「描一圈跑道」这个唯一的核心任务。

## E. 构建 / 签名层

### ★E1. 用 PowerShell 5.1 跑构建脚本，UTF-8 无 BOM 会被按 GBK 解析

**症状**：脚本解析报一堆 `Unexpected token`、中文全成乱码，但脚本在编辑器里看着完全正常。

**根因**：Windows PowerShell 5.1 对**无 BOM** 的文件按系统 ANSI 代码页（中文环境是 936/GBK）解码。中文注释里的字节被误解码后可能产生引号之类的字符，直接把语法搞坏。

**结论**：`build.ps1` **必须存成 UTF-8 with BOM**。

```powershell
$p = '.\build.ps1'
$txt = [System.IO.File]::ReadAllText($p, (New-Object System.Text.UTF8Encoding($false)))
[System.IO.File]::WriteAllText($p, $txt, (New-Object System.Text.UTF8Encoding($true)))
```

---

### E2. `$ErrorActionPreference = 'Stop'` 会让正常构建「失败」

**症状**：javac / keytool / apksigner 明明成功了，脚本却在中间退出。

**根因**：这些原生命令都会往 **stderr** 写正常提示（deprecation 警告、`正在为以下对象生成...`）。`Stop` 模式下 PowerShell 把原生程序的 stderr 当成 `ErrorRecord` 直接终止。

**结论**：构建脚本里用 `$ErrorActionPreference = 'Continue'`，靠 `$LASTEXITCODE` 判断成败。

---

### E3. `keytool` 默认生成 JKS，`apksigner` 需要显式 `--ks-type`

**症状**：签名时报 keystore 格式错误或读不到 alias。

**根因**：JDK 17 的 `keytool` 默认仍可能产出 JKS；`apksigner` 不总是能自动识别。

**结论**：生成时显式 `-storetype PKCS12`，签名时显式 `--ks-type PKCS12`。

## F. 环境 / 虚拟化层

### ★★ F1. MuMu 在 Hyper-V/HVCI 开启时退化到 Snail 模式，LSPosed 崩

**症状**：LSPosed 一直 `System server: not connected`，所有模块不生效；`lspd` 进程能起但立刻 SIGSEGV（`rip = rbp = rsp = 0x314`）。

**根因**：宿主机的 Hyper-V / HVCI 占用了 VT-x，MuMu（VirtualBox）退化到 **NEM + Snail 纯软件模拟模式**；此时 CPU 被错配成 2014 年的 Pentium N3530（Silvermont），LSPosed 的 native 桥接代码走错路径踩坏栈。

但**这不是唯一因素**——实测发现真正的触发机制是**每次开机 KernelSU 触发两次 `service.sh` → 双 `lspd` 竞争**。Snail 模式让这个竞争必输，关闭 HVCI 后恢复可赢。

**结论**：

1. 关闭 HVCI（内存完整性）：`HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity` → `Enabled = 0`，重启
2. 根治双实例竞争：部署 `boot_id` 单实例守卫脚本
3. **最省事**：直接用真机

详见 [05-模拟器与虚拟化.md](05-模拟器与虚拟化.md)。

## 一句话总结

这个项目里真正难的从来不是「hook 怎么写」，而是：

- **为什么 hook 挂上了却没生效**（A2 / A3 / B1——三个层级的「静默失败」）
- **为什么看起来生效了但数据是错的**（B4 / C1——两个「恒为 0」）
- **为什么本机能跑换台机器就废**（E1 / E2 / F1——工具链与虚拟化环境）

代码只占三分之一，另外三分之二在这些判断里。

## G. 判定层（最后发现的一层）

### ★★ G1. 设备时间不对，成绩传不上去（本组唯一真坑）

**症状**：整场计分跑跑完、打卡全过、里程与步频消耗都正常，界面底部显示「正在上传跑步数据…」，然后弹：

```
为了您跑步记录的有效性，请修改为准确的北京时间后再上传记录
```

**根因**：App 拿设备当前时间去跟服务端下发的跑区时间段比对，对不上就拒绝上传。模拟器/刷机设备的默认时钟常跟真实时间差几个小时，跑完才发现，成绩直接作废。

**修法**（跑之前做）：

```
adb shell "settings put global auto_time 0"
adb shell "date MMDDhhmmYYYY.ss"    # 月日时分年.秒
adb shell date                      # 回读确认
```

真机打开系统「自动设置时间」即可。

同一个坑还有一个更早的变体：**点 GO 时**反复弹「跑区有效时间已更新，请重新选择」，重新选跑区也没用——也是时间不对，只是这次卡在进入阶段而不是上传阶段。看到这两条提示中的任意一条，先去校时间。

### G2. 起步阶段配速会「瞬时过快」，别开太快

**症状**：速度设 4.2 m/s（配速 3'58"），但前 200 米界面上的配速先显示 1'28"、3'26"、再掉到 2'43"，被标红「配速过快」。

**根因**：`距离/时间` 的瞬时比值在小样本下抖动大。起步时轨迹刚推进几十米，分子分母都小，比值不稳定；跑开一段距离后才收敛。

**结论**：速度设 **2.4 ~ 3.0 m/s**，离区间边界留余量，不会被瞬时抖动打到红线之外。这只是提示，不影响成绩有效性。

### G3. 一个被推翻的结论，以及它为什么会出现

早期这节写的是「打卡点必须按 1→2→3→4→5 顺序通过，闭环做不到，本仓库未实现」。**这个结论是错的**，闭环路线能正常打卡、正常上传。

错在哪：把两张不同场次的结果页混成了一场。

| 那场的情况 | 结果页 |
|---|---|
| 配置还没打通，0.00 公里、几十秒，压根没进跑区 | 「成绩未达标 · 按顺序通过所有点位」 |
| 完整跑步，打卡全过、里程配速步频全部通过 | 卡在「请修改为准确的北京时间」 |

第一张是**旧记录的结果页**，被当成了第二张的结论。实际上第二张根本没走到判定层，卡在上传前的时间校验上。

**教训**：结果页顶部带着时间段，判负前先核对它是不是你以为的那一场。日志和截图都得带时间戳一起看，否则一次张冠李戴就能在文档里留下一条错误结论。
