# 01 · 环境准备

模块本身只是一个 APK，但它要生效依赖一条不短的链：**root → Zygisk → LSPosed → 模块 → 作用域 → 目标 App**。这条链上任何一环没通，表现都是同一个：「模块不生效」。所以环境准备阶段要能**逐环验证**。

---

## 1. Root

推荐 **KernelSU**（或 KernelSU Next / SukiSU）。Magisk 也可以，但下面的排错路径以 KernelSU 为准。

验证：

```bash
adb shell su -c id
# 期望：uid=0(root) gid=0(root)
```

> KernelSU 的 App 需要装 **KernelSU Manager** 并在里面授权 `su`。

---

## 2. Zygisk

LSPosed 依赖 Zygisk 注入 zygote。Android 13+ 上推荐 **Zygisk Next** 或 **ReZygisk**。

安装后在 KernelSU Manager → 模块 → 确认状态为「已启用」，并**重启设备**。

验证：

```bash
adb shell su -c 'ls /data/adb/modules/ | grep -iE "zygisk|zygisknext|rezygisk"'
```

---

## 3. LSPosed

### 3.1 版本要求

**必须 ≥ 2.2.1**。低版本不认 libxposed 新格式。

### 3.2 安装

把 LSPosed 的模块 zip 刷入（KernelSU Manager → 模块 → 从本地安装），重启。

### 3.3 关键验证：`System server: connected`

```bash
adb shell su -c 'cd /data/adb/modules/zygisk_lsposed && ./lspctl --json status'
```

要看的是：

```json
{
  "systemServerRequested": true,
  "installedModules": 1
}
```

- `systemServerRequested: false` → **LSPosed 没起来，后面全部别谈**，转第 6 节排错
- `installedModules: 0` → 模块没被识别，转 [00-踩坑总览 A1/A2](00-踩坑总览.md)

> 别用 `ps | grep lspd` 判断。`lspd` 进程能起但立刻崩的情况太常见，进程存在 ≠ 桥接成功。

---

## 4. 模块安装与作用域

### 4.1 安装 APK

```bash
adb install -r RunSpoof-v41.apk
```

### 4.2 确认 LSPosed 识别到模块

```bash
adb shell su -c 'cd /data/adb/modules/zygisk_lsposed && ./lspctl --json modules'
```

期望能看到 `com.qf.runspoof`，且 `enabled: true`。

**如果这里没有**：不是作用域问题，是 APK 里的 `META-INF/xposed/` 没被识别。回头查 [00-踩坑总览 A2](00-踩坑总览.md)——用 `unzip -l` 看条目是不是在根目录、是不是正斜杠。

### 4.3 勾作用域

LSPosed 管理器 → 模块 → RunSpoof → 作用域 → **只勾** `com.zjwh.android_wh_physicalfitness`。

> **不要勾「系统框架」**。本模块不 hook 系统服务，勾了只会拖慢开机并可能引发系统侧异常。

### 4.4 让 hook 生效

模块声明了 `autoHotReload=true`，正常情况下强制停止目标 App 再打开即可。若不生效，重启设备。

---

## 5. 验证 hook 真的挂上了

这是**唯一可信的验证方式**——看 logcat 里模块自己打的日志：

```bash
adb logcat -c
adb shell am force-stop com.zjwh.android_wh_physicalfitness
adb shell am start -n com.zjwh.android_wh_physicalfitness/.mvi.splash.SplashActivity
adb logcat -s RunSpoof:V
```

期望看到：

```
I RunSpoof: module loaded, process=com.zjwh.android_wh_physicalfitness, systemServer=false
I RunSpoof: target package loaded: com.zjwh.android_wh_physicalfitness, remotePrefs=true
I RunSpoof: cfg[0] file channel OK, pathPts=19
I RunSpoof: hooked LocationManager#requestLocationUpdates
I RunSpoof: hooked LocationManager#registerGnssStatusCallback
I RunSpoof: sensor register/unregister hooked
I RunSpoof: WifiManager hooked
I RunSpoof: TelephonyManager hooked
I RunSpoof: Location getters overridden (time-based)
I RunSpoof: anti-cheat scrubbed
I RunSpoof: dispatchers started
I LSPosedFramework: config read back: center=<你保存的中心点> speed=4.2 cadence=172.0 radius=39.0 pathPts=19 sig=file:1792369293208:926
I LSPosedFramework: system hooks installed, route=384m, center=<你保存的中心点>
```

**逐行看**：

| 日志 | 含义 | 缺失说明 |
|---|---|---|
| `module loaded` | 模块被加载进目标进程 | LSPosed 没注入，回第 3 节 |
| `target package loaded` | 目标 App 的包级初始化跑到了 | 缺这行说明作用域没勾上 |
| `cfg[0] file channel OK, pathPts=N` | 从 `/data/local/tmp` 读到了 N 个路径点 | 缺这行 = 配置文件没建或没权限，回第 4 节 |
| `hooked XXX` | 某类 hook 挂上了 | 缺某行说明类/方法名对不上（版本差异），见 `hook ... not found in hierarchy` |
| `Location getters overridden` | 坐标 getter 已接管 | 缺这行会表现为「位置完全不动」 |
| `dispatchers started` | 位置/步数/加速度派发线程起来了 | 缺这行后面所有数据都不会有 |
| `system hooks installed, route=...m, center=...` | 全部完成，且打印了**实际生效**的路由长度与中心点 | **最重要的自检行**。`center=` 若等于 `0.0,0.0`（还没设过路线），说明配置没读到 |
| `route=...m, center=...` | 路线引擎就绪 | —— |

## 6. LSPosed 起不来怎么排

按顺序验证，别跳步。

### 6.1 先看是不是虚拟化环境问题

如果你在用 **MuMu / 雷电 / 夜神** 等模拟器，**先读 [05-模拟器与虚拟化.md](05-模拟器与虚拟化.md)**。

典型特征：

```
lspd 进程能起 → 立刻崩 → rip = rbp = rsp = 0x314
lspctl status → systemServerRequested: false
```

宿主机侧查：

```powershell
(Get-CimInstance Win32_ComputerSystem).HypervisorPresent      # True 就是有问题
reg query "HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity" /v Enabled
```

### 6.2 双 `lspd` 竞争

这是实测出来的、比虚拟化更常见的**真实**触发机制：

```bash
adb shell su -c 'ps -A | grep -c lspd'
```

如果开机后能数到 **2**，说明 KernelSU 的 `service.sh` 被触发了两次，两个 `lspd` 抢着建桥接，后起的那个必死，先起的能不能赢看时序。

**临时缓解**：重启模拟器/设备；或把 LSPosed 模块禁用再启用一次。

**根治**：部署 `boot_id` 单实例守卫，让 `service.sh` 在同一个 boot 内只跑一次：

```sh
#!/system/bin/sh
# /data/adb/modules/zygisk_lsposed/service.sh 的守卫包装
BOOT_ID=$(cat /proc/sys/kernel/random/boot_id)
GUARD=/data/adb/lsposed_boot_guard
if [ -f "$GUARD" ] && [ "$(cat "$GUARD")" = "$BOOT_ID" ]; then
    exit 0
fi
echo "$BOOT_ID" > "$GUARD"

# ... 原有的启动逻辑 ...
```

> 注意：原 `service.sh` 末行的 `&` 要保留，它是后台启动的语义，删了会阻塞开机。

### 6.3 确认不是模块文件损坏

不要去猜。直接比对官方包的 sha256：

```bash
# 官方包：https://lsposed.zip
adb shell su -c 'sha256sum /data/adb/modules/zygisk_lsposed/daemon.apk'
adb shell su -c 'sha256sum /data/adb/modules/zygisk_lsposed/manager.apk'
```

和官方 zip 内同名文件逐字节比对。实测这一步能排除掉大量「以为是环境问题，其实是被改过」的情况。

### 6.4 odex 陈旧

如果系统升级或长时间未重启，`daemon.odex` 可能和当前 ART 不匹配：

```bash
adb shell su -c 'cd /data/adb/modules/zygisk_lsposed && ls -l oat/*/'
```

强制重编译：

```bash
adb shell su -c 'rm -f /data/adb/modules/zygisk_lsposed/oat/*/daemon.odex'
adb shell su -c 'dex2oat64 --dex-file=/data/adb/modules/zygisk_lsposed/daemon.apk --oat-file=/data/adb/modules/zygisk_lsposed/oat/x86_64/daemon.odex --instruction-set=x86_64'
```

重启。

## 7. 目标 App 侧

- 目标 App **不能是灰包/重签名版**，否则它自己的完整性校验会先失败
- 首次启动要授予定位权限（否则 App 内部的权限判断会走另一条分支，hook 效果看不出来）
- 建议先手动打开 App 看一眼正常状态（能定位、能开始跑步），再开模块对比
